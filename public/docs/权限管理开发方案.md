## 一、目标（保持原设计，已完成 ✅）

**核心理念：权限以 permission_code 为最小单元。** 角色、用户最终关联的都是 permission_code；菜单只是 code 的可视化勾选载体。

**系统各组件定位：**
```
sys_permission  = 数据存放地
sys_menus       = 外显
sys_role        = 权限组
sys_casbin_rule = 规则验证器
```

Layer 1 (API 权限) 和 Layer 2+3 (行级/字段级数据权限) 均已实现 ✅

---

## ⚠️ Casbin 管什么，新增表管什么（已实现，模型有偏差）

Casbin 模型实际使用 matcher：
```
m = (r.sub == p.sub || (g(r.sub, p.sub) && g2(p.sub, "active"))) && r.obj == p.obj && r.act == p.act
```

与方案差异：
- 增加了 `r.sub == p.sub`：支持用户直接额外权限
- 增加了 `g2` 角色启停：禁用角色时不删除关联，移除 `g2, role_code, active` 即可

其余设计一致。

## 二、整体架构（已实现 ✅）

请求 → JWT 认证 → DataRuleContext 注入 → Casbin 鉴权 → GORM 数据规则查询

## 三、数据流（已实现 ✅）

### API 权限校验流 ✅
JWT → CasbinMiddleware → 通过/拒绝
（CasbinMiddleware 目前作为独立中间件，可加在任意路由组）

### 权限分配流（菜单 → Casbin）✅
前端勾选菜单 → 收集 permission_code → 查 sys_permission → 写入 Casbin p 策略 → LoadPolicy

### 数据权限校验流 ✅
GORM BeforeQuery 回调 → 读 UserContext → resolveDomain → 按角色/用户/部门匹配分配 → 按 rule_id 去重 → mergeRules → Where/Omit 注入

规则定义与分配主体解耦。角色、用户、部门命中的规则都是限制，行条件全部 AND，字段屏蔽取并集；部门分配可配置“仅本部门”或“本部门及全部下级”。

## ⚠️ 七、pkg 层新增组件（与方案目录结构不同）

### 实际目录结构
```
pkg/datarule/
├── types.go        # 类型定义
├── engine.go       # 域注册、UserContext、操作符白名单
├── plugin.go       # GORM 插件（BeforeQuery 回调）
└── register.go     # 生命周期编排
```

### 与实际差异
- 方案设计 `datarule.go/engine.go/injector.go/omit.go/domain.go/provider/gorm.go` 多个文件 — 实际合并为 4 个文件
- 方案设计注册到 `config/register.go` — 实际在 `datarule_router.go` 中通过 `RegisterPluginWithDB` 注入全局 DB
- RuleProvider 由 datarule 业务模块实现，通过 `SetProvider` 注入引擎

4. 缓存失效 ❌ 首期未实现，每次查询都走数据库

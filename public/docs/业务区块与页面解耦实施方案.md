## 1. 先读这一节：不可误解的产品决定

### 1.1 已确认目标

1. 模块必须提供完整、可工作的业务预设，不能要求普通用户从输入框、按钮和接口开始接线。
2. 用户自行创建页面，选择全局业务区块；页面名称、地址和布局由用户决定。
3. 商店、博客、购物车、结算、登录、注册、账号、订单等用途不再决定页面的系统身份。
4. 同一业务能力可以出现在多个页面，也可以位于同页区域、弹窗或抽屉中。
5. 模块控制业务协议和必要结构，用户通过可视化修改被允许的布局、样式、文案与可选区域。
6. 全局区块提供站点内复用；业务计算、鉴权、事务与校验继续属于原业务模块。
7. 前端业务接口采用商品模块已重构的协议：统一 JSON 响应；浏览器可提交 FormData，AI/API 客户端可提交 JSON；同一动作调用同一业务服务。
8. 需要跨页跳转时，由实际按钮、组件或区块配置引用目标页面，不查询全站“某用途唯一页面”。
9. 默认预设优先在区块内部完成必要流程；不能省略流程配置后把故障留给访客。
10. 保留静态发布、不可变产物、共享编译管线和白名单数据绑定。

### 1.2 明确排除的实现

- 把 SiteSlot 改名为 SystemPage、DefaultPage、PagePurpose 后继续要求全站绑定。
- 新建一套独立的“系统业务页面”模型、渲染器和发布管线。
- 根据 URL、页面标题、页面分类或“第一个包含该组件的页面”推断业务身份。
- 强制一个站点只能有一个购物车区块、一个结算页面或一个登录入口。
- 删除绑定后，依靠隐藏按钮、空链接、默认跳首页来掩盖缺失配置。
- 普通用户编辑接口地址、HTTP 方法、鉴权模式、金额字段、JavaScript 或 Jet。
- 由每个全局区块复制实现下单、优惠、库存、权限等业务规则。
- 将旧 HTML 写响应封装进 JSON 的 html 字段，冒充 JSON 数据协议。
- 新增一套独立的表单提交脚本，复制 write-base 的请求、错误、跳转处理。
- 用“商品模块是范例”推断其每个存量分支都已合规；必须逐个回读实际实现。

### 1.3 成功后的使用过程

用户操作：

1. 新建普通页面，填写名称和地址。
2. 从业务区块库选择“购物车与结算”“会员中心”“商品购买区”等预设。
3. 首次使用时创建站点自己的全局区块；已有区块可直接引用。
4. 调整品牌色、间距、文案和受支持的排列方式。
5. 如选择跨页面流程，在可视化选择器中指定目标。
6. 预览正常、空态、失败态、登录态与手机布局。
7. 发布；后续在全局区块中修改共享外观，再发布受影响页面。

用户无需理解 SiteSlot、RuntimeFragment 注册表、接口 URL 或数据库关系。

### 2.1 必须先处理的规则与现状差异

AGENTS.md 不变量 1 目前写“访客请求不查库、不执行 Jet”，仅列两处例外；仓库又已有购物车、账号、订单动态能力。实施 AI 不得自行把所有业务 API 解释成已获准例外。

B0 必须核查实际路由与部署边界，并提出准确的规则校准文本，区分：

- 普通页面 GET：只由 PublicationStore 定位静态产物，不查控制面数据库、不运行 Jet、不解释 AST。
- 明确注册的访客业务 API：按自身鉴权、CSRF、限流和模块契约处理业务数据；不得回读页面/全局区块 AST 来运行页面。

- 存量 HTML 动态片段：单独登记迁移范围，不能因当前存在就继续扩大。

本方案建议新区块动态数据读写统一为 JSON，视图结构在构建期生成。规则文件若需修改，作为单独文档批次处理；不得夹在组件实现里悄悄放宽。澄清前可继续只读盘点和契约设计，不得按自己的猜测扩展运行时边界。

## 4. 强制对照基线：商品模块的 JSON 与表单协议

### 4.1 实际请求链

以商品创建和更新为例：

~~~text
模板声明 data-write / data-write-url / data-write-status
    ↓
write-base 收集表单、按契约整形，生成 FormData
    ↓
fetch POST /api/product/create 或 /api/product/update
    ↓
binding.JSON 按 Content-Type 绑定到同一 DTO
    ↓
service 执行业务
    ↓
pkg/response 输出 JSON + 真实 HTTP 状态码
    ↓
write-base 读取 JSON，显示反馈并执行声明式导航/刷新
~~~

对应证据：

- [商品 Create/Update](../../internal/module/product/inbound/http/product_subject_handle.go)
- [商品创建表单](../../internal/templates/admin/product/product_create_form.html)
- [商品编辑表单](../../internal/templates/admin/product/product_edit.html)
- [binding.JSON 实现](../../pkg/binding/binding.go)
- [write-base 实际 send/onSubmit](../../internal/templates/static/js/ui/write-base.js)
- [响应统一出口](../../pkg/response/response.go)

“只拿 JSON”约束响应与业务协议，不要求所有浏览器请求体都改成 application/json。binding.JSON 的当前名称是历史命名；实现同时接受 JSON、urlencoded、multipart，表单特殊字段经 DTO 的 FormBinder 补充绑定。

### 4.2 对比表

| 维度 | 商品主体写链路 | 现有购物车动态片段 | 新业务区块目标 |
|---|---|---|---|
| 浏览器输入 | 声明式表单，FormData | 片段自身表单和参数 | 沿用统一表单基座 |
| AI/API 输入 | JSON 调同一端点 | 不应直接把 HTML 片段当通用业务 API | 同一业务动作、同一 DTO 和 service |
| 成功响应 | pkg/response JSON | cartAdd/cartSetQty/cartClear/checkout 等返回 HTML 片段 | 统一 JSON |
| 失败响应 | 状态码与对外 message | 存量存在错误提示 HTML 路径 | JSON + 真实状态码，保持用户输入 |
| 页面去向 | data-write-nav 等前端声明 | 片段读取 SiteSlot 后生成链接 | 编译后的显式目标引用 |
| UI 更新 | 前端根据结果处理 | 服务器返回新片段替换 UI | 区块渲染器消费数据/状态 |
| 业务规则 | 原 service | 原 service + 片段适配 | 只在原业务 service |
| 页面身份 | API 不要求某个页面身份 | 导航依赖全站槽位 | API 与宿主页面身份无关 |

### 4.3 后续 AI 必须遵守的表单细节

1. 表单是 UI；写动作提交到 API，不能新增同功能的页面 POST handler。
2. 优先复用现有 data-write 基座；不得为“业务区块”复制第二套 fetch、提示或重定向代码。
3. JSON/form 字段标签按同一业务字段对齐；JSON 隐藏字段与 form 隐藏字段均不得接受客户端伪造身份。
4. 查询走 binding.Query；写动作按当前统一绑定入口处理。不要凭 JSON 函数名推断只接收 JSON。
5. 空串、缺省、false、0、空数组的语义必须分别定义，不能用全局删除空字段破坏“显式清空”。
6. 多选与结构数组按实际序列化形态测试。不得只用 JSON 测试代替浏览器 FormData 测试。
7. 非反射能绑定的形状放 DTO FormBinder；controller 不解析 PostForm、不拼业务对象。
8. 失败保持已输入字段、勾选与当前步骤；不得用错误 HTML 覆盖整个区块。
9. 成功导航由前端动作配置决定；业务成功响应不返回 302、HX-Redirect 或要求前端执行的脚本。
10. JSON 报文的 code 与 HTTP 状态一致；批量拒绝明细放 data.items，禁止部分成功与 skipped 推算。
11. 后端返回事实、业务结果与必要标识，不为每个区块制作 PageResp 或展示字段集合。
12. 原后台写基座的 CSRF 来源不能直接假定适合访客：需核查访客域 token 注入，不能烘进共享静态产物。
13. 无 JavaScript 时按现有 data-requires-js 模式禁用无法工作的提交并给出提示；不自动回退到旧固定业务页面。

### 4.4 不能照抄的存量差异

- write-base 文件头及 send 附近仍有“走 HTMX、不用 fetch”等旧注释；实际 send 使用 fetch，buildBody 使用 FormData。
- 部分商品协议测试注释仍称请求为 JSON、引用已删属性；以实际 DOM、代码和可运行断言为准。
- write-base 仍有跟随重定向及非 JSON 登录页跳转分支；新区块 API 的会话过期必须验收为 JSON 401，不以旧分支作为目标设计。
- write-base 仍能读取 skipped 等旧回执；新业务区块不得依此恢复批量部分成功。
- 商品模块仍有预览、旧页面辅助分支等不同形态；本方案以主体 API 和协议测试为参考，不宣称全模块所有路径已经符合终局。
- X-Message 是现有附加反馈头；JSON 的 message 是业务响应事实。新区块不能在头与 JSON 之间各维护一份不同文案。

本次写文档不顺手修复上述代码。实施批次触及相应文件时，按 AGENTS.md 收口过期注释与重复实现。

## 5. 目标对象与关系

~~~text
模块业务能力（service / contract / API）
           ↑ 被模块前端组件调用
业务组件定义（受支持动作、数据协议、固定结构、可编辑 UI）
           ↑ 被完整预设组合
内置业务预设（代码随模块版本提供，只读）
           ↓ 显式创建站点副本
站点全局区块（已有 block 域管理，受控配置与组件文档）
           ↓ globalref 引用
Page 或 ContentTemplate → PresentationInstance
           ↓ 现有共享发布管线
静态页面外壳与白名单前端增强
           ↓ 访问时
访客业务 API 返回 JSON → 组件更新自身数据与状态
~~~

“模块提供”是责任归属，不要求所有文件都放进 module/service。组件模板和 JS 遵守前端归属，构建注册遵守 builder 归属。

### 5.1 页面

- 继续使用现有 Page；普通页面无需 shop/cart/checkout 等类型才可放业务组件。
- Page 的 URL 占用、预览、发布、回滚继续走既有管线。
- 不在 Page 新增唯一的 businessRole 或必填 systemPageType。
- 既有 PageKind、ContentTarget 必须按实际用途逐项处理；不能用删除所有 kind 的方式顺带破坏内容绑定、首页或 404 语义。

### 5.2 业务组件

一个业务组件应声明：

- 稳定能力标识与协议版本；
- 需要的数据上下文，如当前商品、访客会话、当前订单；
- 可执行动作与各动作 DTO；
- 可编辑 UI 字段及约束；
- 必要结构和状态集合；
- 可公开数据与必须运行时获取的数据；
- 前端资源依赖；
- 缺失必要配置时的诊断定位。

声明必须是封闭结构，禁止扩展成通用接口调用器、查询语言或用户脚本系统。

### 5.3 内置预设

- 是初始化输入：首次创建站点区块时复制默认结构和配置。
- 预设变化不直接覆盖用户已有区块，不参与访客请求。
- 预设版本与业务组件协议版本分开：前者改变默认外观，后者影响能力契约。
- 与已有 Blueprint 的“一次初始化”原则一致，但不必为了复用名称强行把区块预设塞入页面 Blueprint 表。
- 先复用注册与资产体系；只有明确存在持久化业务事实时才增加表。
- 每份预设都必须有完整工作状态与必要动作，不能只是美术外壳。

### 5.4 站点全局区块

- 继续由 block 域持有，复用已有 global/template 概念，不新建平行的 business_blocks 真源。
- 保存组件文档、允许的 UI 设置、显式动作目标、预设来源与版本信息。
- 不保存价格/库存副本、订单内容、访客资料、会话令牌或 CSRF token。
- 站点全局区块只属于一个工程，不提供跨租户共享可写实例。
- 同一源区块可多次引用；每次渲染拥有独立实例标识和交互宿主。

| 访客数据读写 | 对应业务 module 的 inbound/http → service | binding → service → JSON | 拼 UI、返回业务 HTML、决定页面跳转 |
| 模块间业务组合 | 既有 service + contract | 沿用事务、订单与库存契约 | 组件直接调用 model |
| 组件运行时视图 | 前端模板/JS与白名单增强资源 | 状态显示、数据填充、输入收集 | 算金额、做权限最终判定 |
| 表单请求基座 | internal/templates/static/js/ui/write-base.js | 统一序列化、提交、JSON 处理 | 按业务组件名增加购物车/订单分支 |
| 装配 | routers | 注入端口、注册路由与权限 | 复制解析/业务逻辑 |
| 数据迁移 | public/migrations + 显式控制面迁移服务 | 幂等结构变更、数据转换、核对 | 改历史 SQL、直接抹掉旧绑定 |
| 回归与门禁 | architecture / public/test / 组件测试 | 证明边界、协议与行为 | 只检查关键字数量就宣布完成 |

API 的 DTO 与数据契约归原业务域；不要因为 builder/source 是零依赖就把所有运行时协议都塞进去。确需跨前后端共享的配置形状，先在层归属表明确所有者并跑依赖闭包检查，禁止先造万能公共包。

## 7. 预设目录与完整性

以下名称为产品建议，能力 ID 在实施时依据现有注册表定稿。

## 8. 可视化编辑边界

### 8.1 三类配置

| 类别 | 示例 | 处理 |
|---|---|---|
| 外观 | 字体、颜色、间距、圆角、图片比例 | 受限样式属性，可编辑 |
| 合法编排 | 单双栏、白名单区域排序、可选模块显示、按钮文案 | 组件声明范围内可编辑 |
| 业务协议 | 必填字段、价格来源、身份、接口、幂等键规则、付款状态 | 模块控制，不对作者开放 |

第一阶段优先实现属性面板和预定义布局。需要进入区块内部时，只开放有稳定 partKey 的部位；partKey 表示组件内部区域，不是全站页面槽位。

### 8.2 强制约束

- 不能删除业务必需字段、结果提示区、错误反馈区或唯一提交动作。
- 必填约束只能按业务契约允许的方向收紧，不能在 UI 中放松服务端规则。
- 同一页面禁止嵌套 form；组合区块中的多步骤表单按合法兄弟结构组织。
- 禁止 CSS 把必要反馈永久隐藏；可编辑样式有范围与值白名单。
- 控制器、AI/MCP、导入入口都必须执行同一份组件配置校验，不能只依靠检查器禁用按钮。
- 无效配置可保存为草稿，但发布必须报可定位错误；非法结构和越权引用不能成为有效配置。
- 不把“看起来不重要”作为代码判据；每个可编辑属性必须有明确类型、默认值、约束与测试。

### 8.3 状态预览

编辑器至少支持：加载、正常、空态、未登录、校验失败、服务失败、提交中、成功。商品增加缺货/变体未选；订单增加无权限/订单不存在等状态。

预览使用明确标识的模拟数据或受权预览能力，不修改真实购物车、创建真实订单或复用后台身份冒充访客。前端隐藏不是访问控制。

## 9. 配置协议示意

以下 JSON 仅用于说明语义，字段名须在 B1 中结合现有文档协议定稿；不能直接增加一个完全平行的文档格式。

~~~json
{
  "type": "commerce.cartCheckout",
  "schemaVersion": 1,
  "props": {
    "layout": "twoColumn",
    "showCoupon": true,
    "title": "我的购物袋"
  },
  "actions": {
    "continueShopping": {
      "kind": "page",
      "pageId": "57d3ebae-8c19-4e24-b3c5-d52455f44f24"
    },
    "checkout": {
      "kind": "local",
      "partKey": "checkout"
    }
  }
}
~~~

示例中：

- type 是开发者注册的能力，不是用户填写的 API 地址。
- schemaVersion 表示配置协议；未知版本必须明确拒绝。
- props 仅含允许作者修改的属性。
- actions 是封闭动作联合类型，不允许表达式或任意查询。
- pageId 在控制面验证工程归属和发布关系，构建时解析当前语言地址。
- local.partKey 只引用组件声明的部位，不允许任意 CSS selector 或跨区块 DOM 注入。
- 正式 Node 的 ID、类型、属性和绑定遵循现有协议；不因示意省略而删掉现有字段。
- 密钥、身份、金额、token、API URL 不进入作者可编辑配置。

## 10. 动作、链接与详情上下文

### 10.1 首期动作范围

仅提供确有消费者的有限类型：

1. 同组件内切换步骤、展开部位。
2. 同页引用一个明确的目标实例。
3. 导航到具体 Page。
4. 导航到具体 PresentationInstance，或按白名单实体引用取得已发布详情。
5. 普通内容链接可使用既有外链能力；登录、付款、找回密码等敏感流程不接受任意外域回跳。

复用现有链接协议时先核查完整语义，不能仅因为名称类似就复用不匹配的字段。

### 10.2 链接解析

- 页面/实例使用稳定 ID，不持久化可变 URL 作为站内身份。
- 构建期按工程、语言、发布状态解析；两条发布路径使用同一解析规则。
- 最终 URL 从统一发布寻址取得，不在组件里拼语言前缀或 /site。
- 动态业务响应不夹带“推荐去某系统页面”的 UI 决策。
- 访客运行时不为了找链接而查询 page_site_slots、页面 AST 或全局区块 Document。
- 个性化标识仅允许白名单参数，例如订单 ID；最终访问仍需服务端校验归属，参数不是授权。
- 复制页面或区块时，同页实例引用必须重映射；明确的跨页引用保持原目标并提示检查。

### 10.3 缺失、改址、下线与循环

- 草稿可以选择草稿目标，预览明确标识不可公开访问。
- 必需跨页动作的目标未发布、被删除、语言缺失或缺少所需能力时，阻止源页面发布。
- 可选动作由作者显式关闭；不能自动跳首页、自动选第一项或静默隐藏已启用的动作。
- 目标改址要登记反向依赖，重建引用方；过渡期间按已有重定向/发布回执机制保证旧链接可解释。
- 删除/下线仍被活跃必需动作引用的目标，默认拒绝并给出引用对象。
- 目标能力校验基于构建得到的公开能力摘要，不把页面永久标记为唯一结算页。
- 不要求“目标先发布”导致必需跨页引用环无法上线：默认预设使用同区块流程；检测到环时定位并要求改为同页或解除非必要互链。
- 本次不新增整站原子发布系统来掩盖上述环；如果已有发布计划支持某种联合行为，必须先以代码和测试证明。

### 10.4 详情页保持的机制

- ContentTemplate 继续参与每次构建；PresentationInstance 继续承载实体展示与发布。
- 同一业务区块在不同详情页中接收当前实体，不能把商品 ID 固定在共享源区块中。
- 区块声明需要的上下文；缺少当前商品时要求绑定具体商品或禁止发布，不能猜最近编辑的商品。
- 不在本次默认放开“一个实体任意多个 canonical 页面”；如确有需求，另定义主展示页与链接选择规则。
- PublishedEntityLocator 一类实体发布关系不属于 SiteSlot，禁止为了零关键词误删。
- 保留既有独立文档覆盖能力，逐项核对实际行为与过期 SPEC 的差异。

## 11. 运行时、JSON 与前端更新

### 11.1 目标运行时

~~~text
静态 Artifact：区块外壳、样式、合法表单、受控行模板、公开动作配置
前端组件：初始化 → 读取 JSON → 更新自身状态 → 收集输入 → 统一写基座
业务 API：身份/CSRF → binding → service → response JSON
~~~

新区块不依靠服务器回传任意 HTML 来恢复界面。现有 RuntimeFragment 中与迁移范围有关的 HTML 读写消费者逐批替换；无关片段不为这次任务全仓改写。

### 11.2 统一写基座的扩展边界

目前 write-base 的收尾主要面向提示、关闭、导航、整页刷新。业务区块还需要就地更新，需要补充一个通用、经过测试的成功/失败结果分发入口。

要求：

- 先核查既有扩展点；缺失时在原基座扩展，不另写一套 submit 监听。
- 分发原有 JSON 结果和发起表单/实例标识；不为每种组件增加基座分支。
- 具体渲染由对应模块的前端组件处理。
- 每次操作只提交一次；多个区块或重复初始化不能多次绑定事件。
- 保留字段级输入状态与焦点，必要时只更新金额、数量等变化区域。
- 会话过期返回 JSON 401，前端显示受控登录状态；不得接收 HTML 登录页后伪装成功。
- 网关要求浏览器跳转时，API 可返回经服务端生成且验证的业务凭据/受限支付 URL，由前端执行受控支付动作；不得开放作者任填支付地址。
- 前端按钮锁只防误触，订单与支付的幂等由后端负责。

### 11.3 身份、租户与缓存

- 管理员会话与访客会话分开。后台预览不能因同时登录而读取其他访客订单。
- projectId 只是请求参数之一，服务端必须验证请求域、站点与资源归属。
- 私有数据、CSRF 与会话标识不得写入静态产物、共享区块配置、公开缓存键或可复用预览夹具。
- 私有 JSON 响应禁止公共缓存；公开商品数据缓存按真实参数和语言区分。
- 配置与动作清单可公开，但不能作为鉴权凭据；服务端不信任浏览器回传的布局配置或金额。
- 同站购物车的业务状态可以共享；不同区块的展开状态、错误消息、当前步骤应按实例隔离。
- 对同一业务资源的更新，可发布经过注册的局部刷新事件；不能粗暴刷新整页或所有账号组件。

### 11.4 确定性

- 相同文档、区块版本、组件版本、构建数据和语言输入，应产生相同 Artifact 字节。
- 构建时不能生成随机实例 ID、当前时间或短期 token；实例标识由文档节点路径等稳定输入派生。
- 嵌套区块引用继续防环、限制深度、重写 DOM ID/CSS 作用域。
- 运行时签发的短期凭据不进入构建输入。

## 12. 全局区块的版本、修改和发布

当前 block 结构不能直接当作已有完整版本能力。B2 需要补充并验证：

- 乐观并发版本：保存携带 expectedVersion；版本冲突返回 409，不静默覆盖。
- 可恢复的不可变文档快照；预设来源信息和组件协议版本能够追溯。
- 页面构建锁定实际使用的区块版本，编译期间不能再次读取可变最新文档。
- 共享修改写入与受影响依赖标记在同一数据库事务，失败不留一半状态。
- 文件构建、上传、激活仍按已有发布回执与补偿流程，不能假称跨数据库/文件系统一个事务。
- 保存草稿不直接改变线上字节；发布时显示受影响页面和实例。
- 批量准备阶段任一对象失败，整批不自动开始激活；已存在的逐页激活失败需按已有可重放回执恢复，明确不宣称整站瞬时原子切换。
- 取消发布、回滚与重新发布均检查组件协议版本和依赖可用性。

编辑器提供三种明确动作：

1. 编辑共享源：影响引用该区块的页面，显示影响清单。
2. 复制为另一份全局区块：用户显式命名，不自动加后缀；原引用不变。
3. 解除共享并复制到当前文档：重新生成节点 ID，重映射本地引用，保留业务组件限制。

共享源升级不会把私有状态同步给其他用户。解除共享也不解除业务校验。

## 13. 固定槽位的逐项去向

| 旧槽位 | 替代方式 | 必须验证 |
|---|---|---|
| shop | 商品列表/专题页面 + 按钮显式 Page 引用 | 可有多个列表页，“查看全部”各自配置 |
| blog | 文章列表/集合区块 + 显式目标 | 不再根据 blog 角色查地址 |
| cart | 完整购物车区块或同页/抽屉实例 | 加购后目标与宿主页面身份无关 |
| checkout | 区块内结算步骤，或明确结算目标 | 必填信息、幂等、支付异常完整 |
| account | 会员中心区块或页面引用 | 登录成功后目标明确 |
| login | 区块内登录视图或目标实例/页面 | 身份过期时不会退回旧槽位 |
| register | 账号区块内注册步骤或显式目标 | 成功与验证流程完整 |
| forgot | 账号区块内找回入口 | 不要求站点先有专门页面 |
| reset | 区块内重置视图或生成流程指定目标 | 凭据校验、有效期、回跳 |

以下对象不是本次要删除的业务页面槽位：

- adminui.PageSlot / BareSlot：后台渲染出口。
- 页眉、页脚、公告等结构位置：可继续作为布局便利能力；不能被用来强制业务身份。
- 导航菜单位置与普通区块分类。
- 首页路径、404 响应等发布/HTTP 语义。
- 支付回调、第三方认证回调、会话与验证 API。
- 实体到发布实例的真实关联。
- 组件内部受控 partKey。

禁止全仓搜索 slot 后机械删除。

## 14. 站外入口与无页面上下文的流程

取消全站槽位后，系统不能凭空猜出邮件、认证回调该展示在哪。

执行规则：

1. 首先核查真实入口。基线 RequestPasswordReset 给邮件的主要变量为 code，不应假定所有重置邮件都已生成页面链接。
2. 从某区块发起的流程，记录/传递经过验证的目标引用或运行时受限凭据；服务端验证站点归属和目标可用性。
3. 由后台主动发出的邀请、通知等，发送动作显式选择目标，或使用已经配置好的通知模板引用。该引用是具体流程配置，不是全站唯一登录/重置槽位。
4. 支持验证码在区块内完成的流程，可不要求独立落地页。
5. 技术回调 URL 由模块协议管理，处理业务结果；浏览器后续导航由已验证的流程上下文决定。
6. 无目标、目标下线、凭据过期等都要有明确处理；不能回退搜索页面标题、扫描组件或跳未知首页。
7. 外域回跳、伪造目标、跨工程 target、重复回调应有负向测试。

## 15. 发布依赖与引用图

把“本页消费了某全站槽位”替换为实际引用：

- Page/Presentation → 使用的区块与版本；
- 区块/页面 → 显式目标 Page/Presentation；
- 页面/实例 → 实体、集合、媒体、导航等已有依赖；
- 构建产物 → 组件协议/资源版本。

依赖读取与失效写入必须使用同一口径。UI 显示的影响清单与实际重建集合应断言相等，不能各自算一遍。

需要覆盖：

- 共享区块嵌套、同页重复引用、解除共享；
- 修改目标 URL、目标语言上线/下线、目标删除；
- 模板与自动发布实例引用区块；
- 组件实现升级、配置协议升级；
- 页面复制、站点复制后的 ID 重映射；
- 删除前 fail-closed 的引用检查；
- 旧修订、活动产物与可回滚产物仍引用的资源。

过渡期允许离线迁移器读取旧槽位；终局生产渲染、业务 API、构建入口不得依赖旧槽位解析。

## 16. 数据模型与迁移约束

### 16.1 数据模型建议

优先扩展已有 block 域和文档协议。候选事实包括：区块并发版本、不可变修订、预设来源及版本、组件协议版本。是否增加独立修订表，在 B1/B2 根据现有 model 和保留策略定稿。

- 外部实体 UUID，应用生成；内部流水按仓库规则。
- 新时间列使用 create_time/update_time，业务时刻使用 *_at。
- 不新增跨模块表直接查询；新增 Tx 能力放所属模块 contract。
- 构建快照只保存必要的公开配置，不包含用户私有数据。
- 不新增第二份全站用途映射表。
- “哪些页面包含某能力”的派生摘要可用于编辑器过滤和验证，但不能用于隐式选默认页。

### 16.2 旧数据迁移流程

每个迁移批次先 dry-run，输出工程、页面/实例、区块、旧槽位、将转换的动作与冲突原因。

1. 冻结本批源版本；读取具体对象和旧槽位关系。
2. 对每一个真实消费者，把旧角色寻址转换为显式引用。
3. 仅在旧关系能唯一确定目标时自动转换；旧槽位为空、目标失效或用途不明时列出对象，整批拒绝。
4. 不因迁移失败自动创建页面、追加名称后缀、选择第一个候选或抹掉旧链接。
5. 原已发布产物维持可访问，直到替代文档和目标能力通过预检。
6. 数据转换由明确的控制面 service 承担事务；建议由 page 域的迁移服务协调本批，通过其他模块 Tx 契约写入，cmd/routers 只装配与调用。
7. 同一次用户可感知迁移中的文档、引用、版本、依赖标记与迁移记录必须一起提交或回滚。
8. 跨工程迁移按工程建立明确独立任务；不能把“逐工程成功一部分”伪装成一个批量成功。
9. 编译在锁外完成；提交前复核源版本，冲突时返回定位信息。
10. 写出可重放、幂等的迁移记录和前后快照；重跑不得重复创建区块或重复插入节点。
11. 迁移器不直接改页面 AST 的私有语义，调用 builder 提供的校验/转换能力。
12. 全部活跃消费者和产物完成切换后，再删除运行时旧接口与槽位表。

### 16.3 历史迁移与删除

- public/migrations 中历史 SQL 不修改；新增版本化幂等迁移并登记 register。
- 旧迁移可能在新库初始化时先创建旧表，后续迁移再转换/删除，属于迁移历史，不算生产残留。
- 删除槽位表前验证转换记录、活跃文档、发布依赖、后台菜单与权限引用。
- 清理权限点、菜单、词条时逐条列明对象，不用 LIKE 或全库数量作为 seed 门槛。
- SQL 上线前按仓库要求校验；schema 快照若存在，使用生成脚本更新。
- 本文不预占迁移编号，实施时读取当前最大版本。

### 16.4 旧产物与回滚

- 旧 Artifact 可能仍调用 HTML 片段和槽位相关路径，仅迁移数据库不够。
- 切换前枚举活跃产物、待发布构建、旧前端缓存与可回滚版本；明确受影响范围。
- 可在维护窗口完成已批准的一次切换；不得长期双读槽位和新引用。
- 新代码删除旧协议后，不能承诺不兼容旧 Artifact 可直接回滚。应从旧文档经显式转换和当前编译器重建，或明确阻止不兼容产物激活。
- 保留必要的迁移前备份与运维恢复步骤；删除旧代码不等于删除所有历史证据。
- 文件/数据库分离的恢复遵循现有幂等回执，不通过一次 SQL 假装线上文件已更新。

## 18. 验收矩阵

### 18.1 产品与组合

| 用例 | 必须断言 |
|---|---|
| 新站没有槽位配置 | 完整预设可在普通页面运行 |
| 两个自定义购物车页面 | 都可用，不争抢“唯一购物车页” |
| 同页两个同源区块 | DOM ID 不重复，错误和步骤状态隔离 |
| 页面与抽屉各一购物车 | 更新后业务数据一致，界面展开状态独立 |
| 共享区块修改 | 影响清单等于实际待重建集合 |
| 解除共享 | 当前实例独立修改，其他引用不变 |
| 复制页面 | 本地目标重映射，跨页目标可追踪 |
| 商品详情复用 | 不同商品使用同一区块仍显示各自事实 |
| 模板与手工页 | 共用编译行为和链接解析规则 |

### 18.2 协议与数据

| 用例 | 必须断言 |
|---|---|
| JSON 与 FormData 调同一写动作 | 业务效果相等，错误状态与对外文案相等 |
| 缺省/空串/空数组/0/false | 按 DTO 语义处理，无静默清空或漏更新 |
| 网络失败/4xx/5xx | 保留输入、解除提交锁、可重试 |
| 返回 HTML 或跳转登录 | 视为协议不合规，不能当成功 |
| 后端返回金额 | 前端只展示，不重算优惠/合计 |
| 重复点击、超时重试、回调重放 | 后端幂等，不重复订单或扣减 |
| 批量冲突 | 全败，data.items 可定位；无 skipped |
| 未登录/其他用户/其他工程 | 401/403/404 按错误事实，不能读写别人的数据 |

### 18.3 发布与迁移

- URL 改动后引用重建，旧路径按现有策略处理。
- 必需目标下线被引用检查拦截，提示具体消费者。
- 语言不存在时不悄悄混用错误语言。
- 编译中区块被修改，使用冻结版本或提交冲突，不能混合两个版本。
- 同输入编译字节完全相等；预览与发布使用同一冻结输入。
- 私有数据与 token 不出现在 Artifact、全局区块快照、公共缓存。
- 迁移中断后重跑不重复创建、不丢链接、不留下半转换文档。
- 旧未发布文档、活动产物与回滚产物均有明确处置。
- 无槽位表的新环境可以初始化并跑通；由历史迁移升级的环境也能到同一终局。

### 18.4 交互与可访问性

- 1440 / 768 / 375 三种视口，无横向溢出。
- 键盘、触摸、鼠标输入可完成主要流程。
- 焦点、提交中状态、错误提示、必填信息可被辅助技术识别。
- 同页重复组件、抽屉打开关闭、多次扫描不会重复监听或重复请求。
- 禁用 JavaScript 时不提交到无效地址，说明保持可见。
- 手机端不能因隐藏区域而丢失必需操作。
- 可编辑 UI 修改后，正常/空态/错误态都使用同一配置，刷新不恢复旧默认样式。

## 7. AGENTS.md 不变量 1 的校准（已实施，用户确认四档方案）

现状文本：

> **控制面与访问面分离**：访客请求不查库、不执行 Jet、不解释 AST；URL→文件由 PublicationStore
> 状态决定。例外仅两处：POST /analytics/collect（只写一条、响应恒 204）与 AccessGuard 只读访客会话
> （不查 PG、不写、不续期、fail closed）。

问题：仓库里已有购物车、账号、订单等访客业务 API，且 **§4 登记了 22 处 HTML 写响应**。
按现状文本读，这些调用点全部越界；按实际实现读，例外远不止两处。两者必须对齐一次。

校准文本（区分四档，已替换 AGENTS.md 原有的「例外仅两处」表述）：

> **控制面与访问面分离**：
>
> 1. **普通页面 GET**：只由 PublicationStore 定位静态产物 —— 不查控制面数据库、不运行 Jet、
>    不解释 AST。URL→文件的关系完全由发布状态决定。
> 2. **明确注册的访客业务 API**（购物车、会话、订单、AI 采集等）：按自身鉴权、CSRF、限流与
>    模块契约处理业务数据。**不得**为渲染页面而回读页面/区块 AST 或执行 Jet；返回值是数据，
>    不是页面。
> 3. **构建与预览**：在控制面解析文档与模板（导出静态产物），不服务访客请求。
> 4. **存量 HTML 动态片段**：逐个登记在迁移台账里（本文件 §4），随业务区块改造逐批迁成
>    JSON；**不得因为「现在已经是 HTML」就新增同类调用点**。

第 2 条的「明确注册」是判据而非形容词：新增加一个访客业务 API 需要有对应的权限点/路由声明，
与页面路由分开注册（`internal/permission` + `internal/routers` 的既有形态）。

**已实施（2026-10-29，用户确认四档方案）**：AGENTS.md 不变量 1 已换成上述四档文本，作为

## 10. B1 的前置结论（带入下一批）

1. **组件能力声明不用新造一套**：`core.Register` + `SpecProvider`/`PaletteProvider`/`TranslatableProvider`
   已经把「类型标识、可编辑属性、组件库元数据、可翻译字段」覆盖了。B1 要新增的只是
   **动作目标的联合类型**（`page` / `presentation` / `local partKey` / 外链），挂在
   `core` 作为新 interface，而不是塞进 `Props` 的自由 JSON。
2. **B2 的第一件事是加列**：`blocks` 表当前无 `version`、无快照、无预设来源。方案 §12 要求的
   「乐观并发 409 / 编译锁定版本 / 可追溯预设」全部依赖这三样，且必须先做迁移再做服务。
3. **B3 的判据落在两条管线**：`pipeline/compile_site.go` 与 `dependency.go` 是旧映射的唯一注入点，
   显式目标解析要在这两处替换，不能只在组件里改。
4. **B4 有一个未核查项**：访客域 CSRF token 的来源。后台写基座假定有后台会话，访客区块不能沿用
   这个假定而必须先核实（方案 §4.3 第 12 条）。B4 开工第一件事是把这条查清。

## 11. 快照漂移登记（B2 开工时发现，非本批引入）

`bash scripts/schema-snapshot.sh` 在更新 `schema/CURRENT.sql` 时带出了**与业务区块
无关**的差异，必须登记清楚，避免后来者以为它们属于解耦批次：

| 漂移内容 | 判定 |
|---|---|
| `analytics_daily_stats`、`page_views_2026_08`、`master_data_changes_2026_08`、`inventory_stock_movements_2026_08` 四张表 | 历史迁移（含分区表）建出的真实表。上次快照生成在 `5b40d6f3`，此后这些迁移已执行但没重新生成快照 |
| `plugin_migration_ledger` 表与唯一索引 | 同上 |
| `blocks` 段：`version` / `preset_key` / `preset_version` 三列 + 两条约束 | **本批（676）的唯一改动**，diff 内确实只有这 6 行 |

结论：快照漂移是既有欠账（上一次生成之后执行过的迁移没有反映到快照里），
不是本批引入。本批只对 `blocks` 段负责；其余差异随快照一并更新，但**不作为本批的验收内容**，
也不据此声称那些迁移已完成核对。

**给后续批次的判据**：更新快照后先 `git diff schema/CURRENT.sql | grep '^+CREATE TABLE'`
看有没有自己没预期的表；有就查它属于哪个迁移，不要默认"快照本来就该这样"。

## 7. AGENTS.md 不变量 1 的校准（已实施，用户确认四档方案）

现状文本：

> **控制面与访问面分离**：访客请求不查库、不执行 Jet、不解释 AST；URL→文件由 PublicationStore
> 状态决定。例外仅两处：POST /analytics/collect（只写一条、响应恒 204）与 AccessGuard 只读访客会话
> （不查 PG、不写、不续期、fail closed）。

问题：仓库里已有购物车、账号、订单等访客业务 API，且 **§4 登记了 22 处 HTML 写响应**。
按现状文本读，这些调用点全部越界；按实际实现读，例外远不止两处。两者必须对齐一次。

校准文本（区分四档，已替换 AGENTS.md 原有的「例外仅两处」表述）：

> **控制面与访问面分离**：
>
> 1. **普通页面 GET**：只由 PublicationStore 定位静态产物 —— 不查控制面数据库、不运行 Jet、
>    不解释 AST。URL→文件的关系完全由发布状态决定。
> 2. **明确注册的访客业务 API**（购物车、会话、订单、AI 采集等）：按自身鉴权、CSRF、限流与
>    模块契约处理业务数据。**不得**为渲染页面而回读页面/区块 AST 或执行 Jet；返回值是数据，
>    不是页面。
> 3. **构建与预览**：在控制面解析文档与模板（导出静态产物），不服务访客请求。
> 4. **存量 HTML 动态片段**：逐个登记在迁移台账里（本文件 §4），随业务区块改造逐批迁成
>    JSON；**不得因为「现在已经是 HTML」就新增同类调用点**。

第 2 条的「明确注册」是判据而非形容词：新增加一个访客业务 API 需要有对应的权限点/路由声明，
与页面路由分开注册（`internal/permission` + `internal/routers` 的既有形态）。

**已实施（2026-10-29，用户确认四档方案）**：AGENTS.md 不变量 1 已换成上述四档文本，作为
独立的规则文档批次提交，未夹带任何组件实现。同步修正了两处仍按「两个明文例外」表述的代码注释
（`membership` 的 model 与 service），它们引用的约束本身没变，只是计数表述已过时。

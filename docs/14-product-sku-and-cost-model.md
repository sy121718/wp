## 1. 规则（用户口径，逐字复述后形式化）

### 1.1 仓库侧码 与 商品侧码（2026-09-19 用户拍板，取代早期的「两条入口」草案）

**同一条货有两个名字：仓库的，和商品的。**

| 位置 | 长什么样 | 谁决定 | 含义 |
|---|---|---|---|
| 仓库侧 `inventory_stocks.sku_code` | `DRAWERSMOKE_001`（**裸码，不带仓码**） | 运营在新建商品时输入的编码 | 这条货在那个仓里的名字 |
| 商品侧 `products.sku_code` | `SZ_DRAWERSMOKE_001`（= `仓短码_裸码`） | 系统拼 | 商品的对外身份；**前缀标注哪个仓认领了它** |
| 商品侧 `product_variants.sku_code` | `SZ_DRAWERSMOKE_001_RED_V` | 系统拼 | 可售规格的身份（同样带仓码前缀） |

- **仓码前缀只属于商品侧**：仓库里永远看不到 `SZ_` 开头的东西。早期实现把带前缀的整串写进了库存行，
  于是「仓库里那条 SKU」与「商品主体 SKU」同名，两条路互撞（同仓同码两行，见 §9.3 的实测记录）。
- **SKU 输入框 = 可搜索下拉 + 可自由输入**（一个控件承担两种意图）：
  · 下拉选中某仓已有的**裸码** → 那是已经存在的那一行，直接**认领 / 复用**（不新建行）；
  · 自己打一个新码 → 在**勾选的每个仓**各建一行（裸码相同）。
- **多仓**：勾了哪些仓就写哪些仓；某仓已有该裸码的行 → 复用、不重复建（幂等）。
  商品主体 SKU 的仓码前缀取**认领仓**（显式指定的第一个仓；未指定则默认仓），其余仓只建行、不参与命名。
- 捆绑商品**不存在于仓库**（不生成库存行、不分销自己的 SKU），其主体 SKU 一律自定义、恒以 `_B` 结尾。
- **剥离前缀的归属（实测补的一条例外）**：正则是「**商品侧负责剥**」——商品创建/变体生成时算出两个编码再落库。
  但**入库是另一个入口**：`RegisterReceipt` / `RegisterProductionInbound` / 采购建行收到的编码来自**操作者或外部系统**，
  带前缀是常态。所以入库入口按**目标仓短码幂等剥一次**（与商品侧同口径，见 `inventory/service/inventory_stock_sku.go`），
  **空串一律拒绝**（`ErrStockSKURequired`）—— 否则会在仓库侧建出空码或带前缀的行，破坏「仓内 = 裸码」。
  这条例外的边界：只覆盖入库/采购建行；出库、调整、退货、订单路径不改（它们的编码来自既有库存行）。

### 1.2 SKU 编码

- **变体**：`<容器主体SKU>_<属性值1>_<属性值2>..._V`。
  属性段按**属性组的固定顺序**插入（不是按运营点选的顺序）—— 顺序不固定则同一组合会生成不同 SKU。
  仓库侧的对应编码是**剥掉仓码前缀**的那一串（`DRAWERSMOKE_001_RED`）；剥离幂等、大小写不敏感，
  由商品侧在建库存行时完成（§1.1 的两套名字）。
- **捆绑**：以 `_B` 结尾，**主体段必填**（2026-09-19 拍板，取代早期「未填按 URL 段静默派生」的草案口径）。
  新建抽屉给出**系统建议值**（`productCodeSegment(URL 段，为空才回落到商品名) + _B`）并提供「重新生成」按钮，
  运营可改；一旦运营手打过字就不再自动覆盖（修正权限优先于自动派生）。服务端不信任建议值：
  空 / 纯空白一律 `ErrBundleSKURequired`，缺 `_B` 后缀自动补齐（大小写不敏感）。
  商品名与 URL 段都不含 ASCII（派生不出）时，抽屉改提示手填（`admin.products.sku.bundleManual`）。
- 变体的生成方式：按所选属性组做**笛卡尔积**。
- 捆绑成员的三种来源：
  1. 选商品 → 该商品属性笛卡尔积出的 SKU（支持「选中一个商品 → 全部导入」）；
  2. 直接选**仓库 SKU**；
  3. 自己选属性做笛卡尔积生成。
  其余逻辑与变体一致。

### 1.3 成本与价格的归属（重要变化）

- **成本写到仓库**，不再跟着商品本体或变体走。
- **商品本体只有两种价**：原价与促销价。
- 原价默认取成本；可以用「计算器」（按规则改价）自己算着改。

### 1.4 库存数量：跟踪 or 无限（2026-09-19 用户拍板，照 WooCommerce 的语义）

**一个状态只用一种表达方式** —— 「无限」不写进数量列，「还没入库」也不写成一行 0。

| 状态 | 怎么存 | 单行显示 | 商品列表那一列 | 悬浮分仓明细 |
|---|---|---|---|---|
| 无限（不跟踪） | `track_quantity = false`，数量恒 0 | `∞ 无限` | 任一仓无限 → `∞` | 该仓 → ∞ |
| 有货 / 没货 | `track_quantity = true`，数量 = N | N（**0 就显示 0**） | 全部跟踪 → 各仓求和 | 该仓 → N |
| 还没入库 | 该仓没有这一行 | `未入库` | 无任何行 → `未入库` | 该仓 → 未入库 |
| 混合 | 有的无限、有的跟踪 | — | `∞`（**绝不求和** —— 求和等于把无限当 0） | 两类并排 |

- 列与不变量：`track_quantity boolean NOT NULL DEFAULT false` + `CHECK (track_quantity OR quantity = 0)`
  —— 不跟踪的行不允许带数字。**为什么不用可空数量**（WooCommerce 的 `stock_quantity IS NULL`）：
  语义等价，但 NULL 会被 SQL 的 SUM、Go 的 int、前端的加法**静默**当成 0 ——「无限显示成 0」正是这么来的。
  用显式开关后，聚合只对 `track_quantity` 的行求和，任一行为 false 就直接显示 ∞。
- **默认无限**：新建库存行不写数量 = 不跟踪（运营不填就是无限，与 WP 一致）；显式填数字 = 跟踪并写入该数量。
- 扣减与超卖：`track_quantity = false` 的行**不校验可用量、不扣减**（订单照卖）；`true` 沿用既有扣减逻辑。
- **商品列表的「库存」列是查询期聚合的虚拟字段**（真源只有 `inventory_stocks`），悬浮展开分仓明细；
  「无限」不参与数值区间筛选，作为独立的库存状态选项。
- 存量迁移口径：**存量行一律 `track_quantity = true`**（保守）。它们的 0 无法区分为「建行占位」还是
  「卖光了」，把卖光判成无限会直接导致超卖；只有新建行默认无限。

### 1.5 一次保存 = 一个事务；冲突打回给人（2026-09-19 用户拍板）

- **商品的任何一次保存都是一个数据库事务**：商品 + 变体 + 各仓库存行 + 变更记录（masterdata）同事务，
  任一步失败**整体回滚**，绝不留「有商品没库存行」这类半截状态。
  实现：product service 开事务，把 `*gorm.DB` 透传给本模块 model、库存域的 `…Tx` 方法
  （`EnsureVariantStockTx` / `EnsureVariantStockWithExternalTx`）与 masterdata 的 `RecordChangesTx`。
  先例是 masterdata 已有的 `RecordChangesTx(ctx, tx, ...)`；跨模块传递的只有事务句柄，不共享表。
  · **现状缺口（本批修）**：`Create` 里 `CreateWithVariants` 先提交，随后 `ensureVariantStock*` 跑在
    **另一个事务**里 —— 后者失败会留下没有库存行的商品；多仓之后这个缺口会被放大（第 2 个仓失败时
    第 1 个仓的行已经写进去了）。
  · 回滚必须被**测试证明**，不是靠声明：故障注入（变更记录那一段）→ 断言三张表都没有痕迹；
    多仓冲突 → 断言返回中文业务错误且无半截数据；变体清单保存中途失败 → 断言既没新增也没删除。
- **数据冲突打回给人，不自动解决**：剥离前缀的存量迁移（262）若撞出「同仓同码两行」，迁移**失败并在消息里
  列出**仓短码 / 裸码 / 涉及行 id / 各行对应的商品与变体 / 数量 / 创建时间，由人决定保留哪一行 ——
  迁移**不自动加后缀、不改码、不删行**。上线前用只读预检脚本
  （`scripts/check-stock-sku-prefix-collisions.sh`）先看一遍。

## 3. 影响面（改哪些地方）

1. **SKU 生成**：`product_variant.go` 的 `generateSKUCode` 要按新规则重写（主体 + 属性段 + 后缀）；`product_variant_generate.go` 的笛卡尔积要输出固定顺序的属性段。
2. **仓库侧成本**：新增仓库维度的成本载体（见 §4 待确认），`inventory_stocks` 或新表；采购入库的 `unit_price` 是否即成本来源要定。
3. **商品本体价格**：`default_cost_price` 退场（或降级为只读投影）；改价工具（按规则改价）口径从「变体价/成本」改为「本体原价/促销价 + 仓库成本」。
4. **捆绑成员模型**：`bundle_items.options[]` 需要能表达「仓库 SKU」与「属性笛卡尔积」，而不只是已有变体 ID；`inventory_bom_items` 的父/子维度是否同步到 SKU 要一并决定。
5. **订单/购物车**：仍按容器价成交（已定），但成员若来自仓库 SKU 而无对应变体，履约/扣库存路径要能按 SKU 走。
6. **存量数据**：现有 SKU 一律不重写（编码规则变更只约束新建）；成本搬迁需要迁移脚本与过渡期双向同步策略。

## 4. 已确认（2026-09-19 用户逐条回答）

1. **「仓库 SKU」的实体**：就是**仓库现有的 code**（仓库侧已有的 SKU 编码），不另建目录。
2. **成本粒度**：仓库侧**只记一个当前成本价**，不做成本流水。核算归采购侧（可以不走采购流程、由外部核算后导入入库）。
3. **多仓与「原价默认取成本」**：**同一个 SKU 可以存在于多个仓库**；「原价默认取成本」取**所选 SKU 来自的那个仓库**的成本。即成本与库存一样是 (仓库, SKU) 维度。
4. **属性段编码**：用**属性值**（不是属性 key）。**属性组只是容器** —— 两个颜色 × 两个口味 = 4 个 SKU（笛卡尔积），属性段顺序按属性组的固定顺序。
5. **捆绑成员**：**允许直接选仓库 SKU**，并在此基础上按笛卡尔积算出组合。
6. 补充约束（同批确认）：
   - 新建商品用**自定义 SKU** 时，若选了仓库，SKU 自动附加仓库码；
   - 需要一个**默认仓库且不可删除**，给「暂时不知道怎么处理」的商品兜底；
   - **创建商品时自动入库**（建库存记录）。

7. **唯一性（用户口径，2026-09-19 补充）**：
   - **商品内唯一**：现状即如此 —— `product_variants` 上已有 `UNIQUE (product_id, sku_code)`（还带一个 `UNIQUE (product_id, option_values)` 的偏索引，管的是「同一组合不重复生成」）；
   - **仓库内唯一**：同一仓库不能有重复 SKU —— 给 `inventory_stocks` 加 `UNIQUE (warehouse_id, sku_code)`（现在只有 `UNIQUE (variant_id, warehouse_id)` 与一个**非唯一**的 `(project_id, sku_code)` 索引）；
   - 所以**不要求全局唯一**：同一个 SKU 文本允许出现在不同仓库（这正是「(仓库, SKU) 维度」的直接结果）。
   归**批次 A**（inventory 侧）；加索引前要先扫存量重复（有重复则迁移必须显式报错而不是静默丢弃）。
8. **容器主体 SKU 的落点（2026-09-19 补充，实现时发现的表结构缺口）**：
   `products` 表**没有 SKU 列** —— 而「容器主体 SKU」（变体商品的 `<仓短码>_<仓SKU>`、捆绑商品的
   `…_B`）需要一个唯一落点：捆绑自 238 起不再生成首个变体，变体行也只存变体自己的 SKU。
   → 新增 `products.sku_code`（迁移 246）+ **项目内唯一**偏索引
   `UNIQUE (project_id, sku_code) WHERE sku_code <> ''`（存量空串不参与约束，可逐步补齐）。
9. **唯一性的最终形态（2026-09-19 用户拍板）**：
   - **主体容器唯一**（`products.sku_code` 项目内唯一）—— 这是唯一强约束；
   - **变体不管**（只保留 `product_variants (product_id, sku_code)` 这条现状约束，不额外收紧）；
   - **捆绑成员不管**：两个捆绑可以选同一个成员 SKU，成员不是身份；成员组合是否重复不做校验。
     （用户结论：「主体容器唯一就行了，变体是不管的，我觉得这个最合适」）
   - 后缀天然区隔：变体以 `_V` 结尾、捆绑以 `_B` 结尾，主体无后缀，命名上不会互相撞车。

## 7. 与主流电商模型对照（为什么这套是合理的）

用户提问：**「商品主体容器才是传统意义的商品，剩下的都是仓库码，这样合理吗？常规系统怎么做？」**

先回答第二问。主流电商/PIM 的分层是**三段**：

| 系统 | 商品层 | 可售层 | 库存层 | 仓库/SKU 的关系 |
|---|---|---|---|---|
| Shopify | Product | Variant（`sku` 全局唯一，可空） | InventoryItem → InventoryLevel(location, available) | 仓库（location）**不进** SKU 编码 |
| WooCommerce | Product | Variation（SKU 全局唯一） | 第三方多仓插件按 location 存 | 同上 |
| Magento | Configurable Product | Simple Product（SKU 全局唯一） | MSI：`inventory_source_item(source, sku, qty)` | 仓库是**库存维度**，SKU 仍是全局 |
| SAP / NetSuite | 物料（Item 号全局） | 同层 | 库存按工厂/地点（Werks/Location） | 物料号不带仓 |

也就是说：**主流把「仓库」放在库存维度，而不是放进 SKU 的身份里**。

再看本项目的模型（＝用户口径）：

```text
products（主体容器 ＝ 传统意义上的「商品」）
   · 承载：名称 / 描述 / SEO / 分类 / 品牌 / 标签 / 原价 / 促销价
   · 新增：products.sku_code ＝ 容器主体 SKU（项目内唯一，迁移 246）
product_variants（规格组合 ＝ 可售单元）
   · SKU 文本 ＝ <主体SKU>_<属性值…>_V（属性值按属性组固定顺序）
inventory_stocks（(仓库, 变体) 的库存）
   · sku_code ＝ **仓库侧裸码**（不带仓码前缀）
   · cost_price ＝ (仓库, SKU) 的当前成本（NULL = 未核算）
   · track_quantity ＝ 是否跟踪数量（false = 无限，见 §1.4）
```

**多出来的那一层映射就是「仓库 SKU」**：主体 SKU 是「我们自己的身份」，仓库 SKU 是「仓库/渠道的身份」，
两者通过「从仓库选 SKU」建立映射。

### 结论：合理，而且这正是「多货源 / 第三方仓」场景下的常见形态

- 跨境电商铺货、3PL 代发、店仓一体这类业务里，「渠道 SKU / 仓库 SKU」是**客观存在**的（对方的编码我们改不了），
  所以必须有一层「我们的商品 ↔ 对方的 SKU」的映射。主流的「SKU 全局唯一」预设了「SKU 由我们自己定、
  且只有一个货源」，在这个前提下它更简洁。
- 本项目的额外约束（同一 SKU 允许存在于多个仓库、仓库内唯一）是这套映射的自然结果：
  SKU 字符串的**身份范围下沉到仓库**。

### 必须守住的三件事（否则这套模型会反噬）

1. **内部身份永远是 `variant_id` / `product_id`（uuid），不是 SKU 字符串**。
   跨仓汇总、订单、报表、促销命中都按 id 聚合；SKU 串只用于展示、拣货、与仓库/渠道对账。
   一旦某处用 SKU 串当关联键，多仓场景立刻分叉（同一个 id 在不同仓有两个串）。
2. **历史单据必须快照 SKU 文本**，不能只存引用：仓库换码、商品换仓都会让 SKU 串变化。
   （现有设计已经这样：库存流水 / 采购行 / 订单行都冗余存了 `sku_code`。）
3. **价格挂在主体/变体，不挂在 SKU 串**：多仓同款的价格应天然一致（用户已定：主体只有原价与促销价，
   成本才按 (仓库, SKU) 记）。

## 8. 变体组合与捆绑成员：预览—保存模型（2026-09-19 用户拍板）

用户口径原话：「变体 sku 也是一样系统生产 + 可编辑，生产只是显示，并不会存入数据库，必须保存才行，
所以删除不是删除，是相当于清除前端显示，不存入数据库」。

形式化（变体生成抽屉与捆绑成员配置器**共用同一套**）：

| 动作 | 落库？ | 语义 |
|---|---|---|
| 勾选属性值 → 点「生成」 | **否** | 把所选值的笛卡尔积**追加进前端清单**（去重）；SKU 由系统生成，**可逐行编辑** |
| 删除 / 取消勾选某行 | **否** | 只是从**前端清单**里移出；库里什么都没变 |
| 点「保存」 | **是** | 以清单为准落库（新增缺失的、更新改过的 SKU、删除清单外的既有变体） |

两条关键设计（否则「删了又回来」）：

1. **抽屉打开时的清单种子 = 库里已有的变体**，不是重算笛卡尔积。
   这样上次删掉的组合不会自己冒出来；只有运营**再点一次「生成」**（显式动作）才会追加回来。
2. **保存的守卫**：清单外要删的既有变体若**有非零库存或被引用**，跳过并在结果里逐个列出
   （不静默、也不因为一行拦不住就整批失败）。理由与商品的批量删除同一条约定。
   覆盖面（2026-09-19 实现批记录）：**已覆盖**库存非零与 BOM 引用（inventory 侧）；
   **待补** —— 捆绑成员引用（`products.bundle_items.options[].variantId`）与订单 / 库存流水里的
   历史快照。两者都需要 product model 新增具名查询方法（跨聚合只能从 model 出口），
   归入**批次 C**（捆绑成员来源那一批，正好要动 bundle_items 的读写）。

> 变体 SKU 文本的编辑只作用于「保存」这一步：预览里的编辑不落库，保存失败时以库里的值为准（不静默覆盖）。

## 9. 仓库 SKU 与商品 SKU 的关系：外部编码映射（2026-09-19 用户追问后定稿）

用户追问：「仓库里只有仓库码，但仓库里也应该有直接标注了各个属性的 SKU 吧 —— 那怎么算每个口味卖多少？
只能走商品吗？还是说一开始就在仓库算好、而不是从商品那边笛卡尔积生成？那样变体就都是直接选仓库，
或者商品自定义然后回填仓库了。捆绑也该改逻辑了。怎么样最好？」

### 9.1 结论：属性属于**商品**，仓库侧只回答「这条货在这个仓叫什么」

| 维度 | 真源 | 理由 |
|---|---|---|
| 规格（颜色 / 口味 / 尺码…） | **商品侧**（属性组 + 值 → 笛卡尔积 → variant.option_values） | 「红色」是商品的定义，不随仓改变；仓库里的红货只是同一个 variant 的一条库存 |
| 销量统计（每个口味卖多少） | **按 variant 聚合**（订单行已快照 variant_id / sku_code / option_values） | 从仓库编码里解析属性是把**字符串解析当业务逻辑**：遇到 `HS-RD-SM`、`RED_BIG` 这类对方命名就崩；而且同一 variant 在多仓有多个编码，按编码聚合会把一件货拆成几份 |
| 「这条货在这个仓叫什么」 | **仓库侧**（外部编码） | 第三方仓/平台仓的编码我们改不了，只能映射 |

### 9.2 三个方案对比

| 方案 | 形态 | 问题 |
|---|---|---|
| A（**推荐**）商品为主 + 外部编码映射 | variant 仍是规格的真源；仓库侧每一行库存带一个 `external_sku`（对方编码）；两边靠映射连起来 | 需要多一列/一张表；但两个来源（从仓库选 / 自定义回填）都自然落到它上面 |
| B 仓库为主 | 先在仓库建好带属性的 SKU，商品只是它们的组合视图 | 属性的真源跑到仓库，商品侧无法独立表达「这个商品有哪些规格」；多仓时同一商品在不同仓的规格集合可能不一致 —— 商品页没法渲染 |
| C 双向同步 | 两边都写，冲突时再合并 | 同步是长期成本，且冲突没有确定性解法；本项目控制面/访问面分离的原则也不允许 |

### 9.3 落地形态（A）

- `inventory_stocks` 加 **`external_sku`**（可空）：这条库存在**对方系统**里的编码（第三方仓 / 平台仓自己的编码）。
  未填 = 对方就用我们给的编码（自营仓的常态）。
  ⚠️ 别和 `sku_code` 混：**`sku_code` 是这条货在我们仓库里的名字（裸码，§1.1）**，
  `external_sku` 是它在**别人**系统里的名字 —— 一个是我们起的，一个是对方给的。
- **映射是 N:1，不是 1:1（2026-09-19 用户补充场景后修正）**：用户场景原话 ——
  「我有一个产品叫 go 35000，有十几个口味，但是计算的时候其实这些都是一个价格在仓库的」。
  即**一个商品的多个变体在仓库侧共用同一个编码/同一条成本记录**（口味合并管理，常见于第三方仓与平台铺货）。
  于是：
  · **不建** `UNIQUE (warehouse_id, external_sku)` 这种偏唯一索引 —— 它会把「12 个口味共用 1 个外码」判成冲突。
    只建**普通索引** `(warehouse_id, external_sku)`（供按外码反查用）。
  · 唯一性改为**弱校验（service 层写入时）**：同一个 `external_sku` 在同一个仓库内必须指向**同一个 `product_id`**
    —— 多口味共用一个外码合法（这正是口味合并）；两个不同**商品**共用一个外码是数据错误，报业务错误。
    这条不放进索引：它跨行、且要给出可读的业务错误。
  · 本表仍保留 `UNIQUE (warehouse_id, sku_code)`（我们自己的 SKU 仓内唯一，不受外部编码影响）。
- **成本与映射是两件事，别混**：`inventory_stocks.cost_price` 仍按 (仓库, 变体) 存「当前成本」；
  十来个口味共用同一个成本值时，就是这十来行**写同样的值**（不需要新表，也不需要 cost_group 抽象）。
  「仓库那边一条 SKU 更好算」在实现上落在「**成本记录可以共用**」，而**不是**「把聚合键换成仓库 SKU」。
- **利润的两个数已经在订单行上**：`order_items.unit_price` + `order_items.cost_price`（成本在建单时就快照）。
  报表按 `variant_id` 聚合即可，不需要、也不应该改成按仓库 SKU 聚合。
  ✅ **已完成**（2026-09-19 商品域评审收口批）：成本快照的来源已改为「该变体在**该行归属仓**的
  当前成本」—— `internal/module/product/service/product_variant_snapshot.go` 不再读
  `product_variants.cost_price`（变体级），改经库存域的 `ResolveVariantWarehouseCosts`
  （归属仓 = 行上显式 WarehouseID，为空按库存域既有的归属仓解析规则取默认仓；与扣减同一个入口）。
  未核算（`inventory_stocks.cost_price IS NULL`）时订单行成本**留空**：迁移 256 把
  `order_items.cost_price` 改为可空（去掉 NOT NULL DEFAULT 0），Go 侧为 `*int64` / 对外 JSON 的
  `null` 与 0 严格区分（0 是合法的显式成本：赠品 / 内部划拨）。
  出库时刻的成本另在 `inventory_stock_movements.unit_cost` 留痕（迁移 256），改价不再影响历史。
  `product_variants.cost_price` 与 `products.default_cost_price` **本批不删**（仍是既有数据与管理面
  字段），删列要另开一批并先做数据搬迁。
- 变体的两条来路（就是 §1.1 那一个输入框的两种填法，2026-09-19 修正为**认领 / 复用**）：
  1. **下拉选中仓库已有的裸码 = 认领**：那行本来就在，直接绑定到新商品的变体（属性由运营在商品侧确认，
     **不从编码解析**），需要时补 `external_sku`；**不再新建一行**（这正是早期实现撞
     `UNIQUE (warehouse_id, sku_code)` 的原因：仓库侧被写成了带前缀的码，两边同名）。
  2. **自己打一个新码 = 建行**：商品侧生成商品/变体编码（带仓码前缀），仓库侧写**剥掉前缀的裸码**；
     勾了几个仓就在几个仓各一行，已有该裸码的行复用（幂等）。
  两条都只改映射，不动「属性属于商品」这条。
- **捆绑不受影响**：成员引用的是 variant，扣减按 BOM 展开到成员各自的归属仓 —— 与外部编码无关。
  「捆绑也该变逻辑」只发生在**成员来源**上（可引用变体 / 可引用仓库 SKU），不发生在成员的身份上。

# 控制器精简与「JSON / 页面同一链路」的验证（2026-10-07）

> 状态：**验证结论 + 建议**，未动代码。
> 触发问题：① 控制器还能不能精简？② JSON 接口与后台页面能不能完全走同一个链路？
> ③ 如果可以，是不是直接改造所有模块？
>
> 结论摘要：**判定层与取数层已经是同一条链路**；差异只剩「参数绑定方式」与「响应呈现」两处。
> 其中只有**参数绑定**是真正可删的重复（机械、无迁移、可分批）；「一个入口两种呈现」不建议做。
> **不建议一刀切改造所有模块**，按模块分批做参数绑定收敛即可。

## 1. 实测基线（690 条路由的当前状态）

| 项 | 实测 |
|---|---|
| 路由 | `/api/*` **317** 条；`/admin/*` 与 `/workbench*` 页面 **338** 条；其它 35 条（公开面 / 静态面） |
| 判定链 | 两者同一条：Session → CSRF → Casbin。API 是**组级**挂 `CasbinMiddleware()`（按实际请求路径 enforce）；页面是**逐路由**挂 `CasbinMiddlewareForPath(API 路径)` |
| 页面侧的权限声明 | **283 处** `CasbinMiddlewareForPath(...)` 调用点（借对应业务 API 的权限点） |
| 取数层 | 每个 `SetupXxxPages` 收到的都是**本模块服务契约**，与 API 用的是同一个实例（`SetupOrderPages(..., svc ordercontract.OrderService, ...)`、`SetupProductPages(..., products productcontract.ProductService, ...)` …） |
| 参数绑定 | 页面文件里手写 `c.Query(` **320 处**，`ShouldBindQuery` 只有 **6 处**；API 文件里 `c.Query(` 93 处（其余走 dto 绑定） |
| 响应呈现 | API → `response.Success/ErrorWithMessage`（JSON）；页面 → `c.HTML`（Jet 整页） |

## 2. 结论

### 2.1 「同一个链路」已经成立的部分

- **判定链同一条**：都是 Session + CSRF + Casbin，只是挂载粒度不同（组级 vs 逐路由）。
  页面借 API 的权限点，是为了绕开「页面路径不在权限点表里、按页面路径 enforce 会全员 403」。
- **取数层同一个**：页面 handler 与 API handler 调的是**同一个 service 的同一个方法**。
  实测样板：`/api/order/coupon/list` 走 `h.svc.ListCoupons`，`/admin/coupons` 走
  `h.orders.ListCoupons` —— 同一个实例、同一个 dto（`orderdto.CouponListReq`）。

所以「完全同一个链路」这个问法里，**判定与取数不需要再统一**；需要统一的是下面两处。

### 2.2 真正可删的重复：参数绑定

页面 handler 里 320 处手写 `c.Query("status")` / `c.Query("keyword")` / `c.Query("project")`，
而 API 侧同一个查询用 `ShouldBindQuery` + 模块 dto 一次绑完。同一份字段表写了两遍，
表现是**同一个筛选条件在 API 与页面上各有一份解析**（改一个参数名要改两处，漏一处不报错、
只是那个筛选在页面上静默失效）。

收敛方向：页面也用它**已有的** dto 绑定（`orderdto.CouponListReq` 之类），页面独有的
`page` → `Offset/Limit` 与筛选回显用一层小适配器补上。

- 收益：手写 `c.Query(` 大幅下降；同一份字段表只留一份。
- 代价：**无迁移、无行为变更**（绑定结果等价），可以一个模块一个提交地做。
- 判据：页面文件里 `c.Query(` 计数下降，且该模块的页面渲染测试全绿。

### 2.3 不建议做的两件事

**(a) 「一个入口按 Accept 分档」**（同一个 URL 返回 JSON 或 HTML）。
它要求页面与 API 共用一个 URL，与「页面在 `/admin/*`、API 在 `/api/*`」的既有边界冲突；
而页面 handler 的主体（20+ 个模板键的装配、空态分支、分页 URL 拼装）**本来就不是 JSON 侧的重复**，
统一不掉。收益只是省掉一次「绑定 + 调用」，代价是 URL 语义混乱 —— 不值得。

**(b) 把 283 处 `CasbinMiddlewareForPath` 一次性收敛成「页面按自己的路径 enforce」**。
技术上可行（给每个页面建权限点，让组级 Casbin 按页面路径判定），但它是一次**行为变更**：
现有角色的 Casbin 策略是按 API 路径存的，切换后**所有非超管角色都会失去页面访问**，
必须同批写迁移授权 + 运营重新授权。收益（删 283 行）远小于上线风险，**不应与参数绑定收敛同批**。
要做得单独立项，判据是「页面路径在 `sys_permission` 里逐条存在，且迁移为超管与既有角色补齐策略」。

## 3. 建议的改造顺序

1. **按模块做参数绑定收敛**（§2.2）—— 机械、可验证、无迁移。一次一个模块，判据见上。
2. **不做**「一个入口两种呈现」（§2.3a）。
3. **单独立项**再谈页面权限点收敛（§2.3b），并先写好迁移与重授权方案。

「直接改造所有模块」的建议：**按模块分批做第 1 项**。理由不是工作量大，而是其中只有第 1 项是净收益；
把它和另外两项混在一批里，会把「删重复」变成「改行为」，出问题时无法区分是哪一个引起的。

实测待改量：页面文件里 **320 处**手写 `c.Query(`，分布在 46 个文件、约 20 个模块。
建议一次一个模块（该模块的页面文件 + 它的页面渲染测试），判据是「该模块 `c.Query(` 计数下降、
页面渲染测试全绿」；不要按「全仓 grep 替换」推进 —— 页面里的 `c.Query` 有一部分是页面独有的
一次性参数（`id`、`page`、回显值），机械替换会把它们塞进 dto。

## 4. 一个反例：不要统一掉什么

页面 handler 的**视图装配不是重复**。以 `/admin/coupons` 为例，它在调完 `ListCoupons` 之后要算：
工程上下文（含「读不到工程就整页降级」的分支）、状态筛选的**生效值**（白名单内归一、白名单外原样回显
并置 `valid=false`）、分页 URL（带全部筛选条件）、空态分支、20+ 个模板键。
这些只服务页面，JSON 侧一个字都不需要 —— 把它们「统一」进共用层，等于让 JSON 接口背上一堆
只为模板存在的键（正是 AGENTS.md 里「Go 替模板做的事」那一类）。

# 17 · AI 助手 与 运营概览（设计与实施计划）

> 状态：**设计待评审**。涉及模块：`ai` / `workbench` / `order` / `user` / `analytics` / `page` / `project` / `permission`。
> 上游依据：[`16-ai-session-and-cache.md`](16-ai-session-and-cache.md)（会话层三机制）、
> [`13-module-inventory.md`](13-module-inventory.md)（模块清单权威）、`AGENTS.md`（不变量与红线）。
> 本方案**不改**会话层已有机制，只在其上补「工具」与「渲染」两块。

## 0. 一句话

把后台首页做成运营驾驶舱；同时在全局引入一个能读能写、可被外部客户端复用的 AI 助手——
工具由各模块自己声明，输出用现有基座控件渲染。

## 1. 范围

### 1.1 本方案要做

1. **概览页重构**：时间筛选条 + KPI + 图表 Tab + 排行榜 Tab，数字全部跟随筛选。
2. **客户域独立**：从「交易」目录拆出「客户」一级目录，原「交易」更名「订单」；
   客户概览 / 客户列表（加筛选）/ RFM 分析 / Cohort 分析四个页面。
3. **AI 悬浮球**：全局入口，带页面上下文，能读数回答，也能把筛选「做好」交给用户一键应用。
4. **工具注册表**：各模块在 `inbound/mcp` 下声明工具，装配期汇总成唯一注册表。
5. **AI 输出渲染**：AI 出 spec（组件树 + 动作），服务端校验后渲染成基座控件。
6. **MCP 对外端点**：同一份注册表用官方 SDK 暴露为 `/mcp`，供外部客户端（如 DSH）连接。
7. **补齐 order 只读聚合接口**：区间订单数 / 销售额 / 按日趋势 / 待处理 / 商品销量与热销前十 / 新客数。

### 1.2 明确不做

- **不做子代理与多代理编排**（DSH 那套团队模式）：后台助手的任务是查数、筛选、出图，
  引入多代理只会让「它为什么改了我的订单」更难追。
- **第一轮不做「插件给 AI 加工具」**：插件体系（`06-plugin-system.md`）是建站能力扩展，
  与 AI 工具是两回事；先让内建模块跑通，再评估 `tools` 段进 manifest。
- **不覆盖 `/workbench` 编辑器**：那边有独立外壳，先只做 admin 侧（`admin/layout.html`）。
- **不做流式的花活**：流式只保证「能边生成边显示」，不做逐 token 的排版重排。

## 2. 架构分层（DSH 调度模式 → go_wp）

| 层 | 形态 | 载体 |
|---|---|---|
| 常驻层 | 总是进上下文的规则与口径 | AI 读的站点规则文档（复用 `AGENTS.md` 判据，不另写一套） |
| 按需层 | 目录摘要 + 按需加载全文 | 模块能力手册（素材来自 `13-module-inventory.md` 与各模块 `CLAUDE.md`） |
| 能力层 | 工具声明 + agent loop | 各模块 `inbound/mcp` → 装配期汇总注册表 → ai 模块驱动循环 |
| 治理层 | 压缩 / 审批 / 审计 / 剪枝 / 渲染 | `docs/16` 折叠（已有）+ 本方案新增的审批、审计、工具结果剪枝、spec 渲染器 |

**核心主张**：模型不直接操作系统，它在注册表划定的能力空间里做选择；系统负责「给什么、
能聊多久、能不能做、做完长什么样」。

## 3. 设计决策

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| D1 | 工具由**拥有数据的模块**在自己 `inbound/mcp` 下声明，装配期汇总成唯一注册表 | 表隔离：跨模块直查表被禁止；「谁能读这张表」的答案只能是拥有它的模块 | 每加一个工具都要在模块内落一次文件与一次装配注册 |
| D2 | 工具形状对齐 MCP；进程内用 in-memory transport，对外用官方 go-sdk 暴露 `/mcp` | 一份定义两种消费，避免第二套工具；官方 SDK 有进程内传输，不必为此引入网络层 | 引一个第三方依赖（`modelcontextprotocol/go-sdk`） |
| D3 | 鉴权复用 Casbin：工具 = **权限点 + 类型化参数 schema + handler** | `CasbinMiddlewareForPathAs(obj, act)` 已支持「显式权限点 + 动词」，页面写操作走的就是它 | 工具必须显式声明权限点，漏了就全员 403（同权限点注册的既有教训） |
| D4 | **内部** AI 助手使用全局统一工具清单；**外部** `/mcp` 按 token scope 裁剪 `tools/list` | 工具集一变前缀就变，provider 缓存整段作废（`docs/16` §3）；而外部客户端看不到无权限工具是更好的体验 | 内部助手会看到自己无权调用的工具，越权在 handler 里拒 |
| D5 | spec 只描述「组件 + 数据源 + 参数」，**不携带数据** | 数字必须来自服务端查询，否则模型会编数字（`admin/dashboard.html` 记着的 P0 教训）；与不变量 4「Binding 不是 Query DSL」同源 | 每个组件都要有一份对应的数据源实现 |
| D6 | spec 与 action 同一协议两半：`{blocks, actions}` | 出图与「帮你筛好」是同一个回答的两部分，分成两套协议必然漂移 | 前端要有 action 运行时 |
| D7 | 渲染在**服务端**（Jet 片段），复用 WBUI 基座 | 后台全是 Go + Jet + HTMX；服务端渲染的白名单由 Go 类型系统兜底；WBUI 的 `scan` + `htmx:afterSwap` 已就绪 | 要写一层 spec → 片段的渲染器 |
| D8 | 写操作三件套：**确认 + 幂等 + 审计** | 外部 AI 会重试；写权限外借必须可追 | 每个写工具都要多写这三样 |
| D9 | 页面上下文只注入 `path + query + 菜单标题`；筛选维度从工具 schema 反推 | 40+ 页面逐个登记语义就是第二份真源，必然腐烂 | AI 对页面的理解不如「页面自述」精确，需要它明说自己的理解 |
| D10 | 「能力手册」按需加载，不进系统提示词 | 与 DSH 技能层同构；省 token 且随代码演进 | 要有人维护手册与 `docs/13` 的一致性 |

## 4. 要补的接口清单

> 「现状」一列是核实过的事实，不是估计。

### 4.1 order（本方案最大的后端工作量）

| 接口 | 输入 | 输出 | 现状 |
|---|---|---|---|
| 区间订单摘要 | projectID + from/to | 订单数、净销售额、待处理数 | 只有 `CountByStatus`（无时间窗）、`SummaryByUser`（单客户）、`SpentTotalsByProject`（每客户累计） |
| 按日趋势 | projectID + from/to | 每天订单数与销售额 | 无 |
| 商品销量 | projectID + from/to + limit | 按商品的销量与金额 TopN、总量 | 无；`order_items` 已有 `product_id` / `quantity` / `unit_price`（单位：分） |
| 新客数 | projectID + from/to | 首单落在区间的客户数 | 无 |

口径必须复用既有唯一真源：净额表达式 `orderNetTotalSQLExpr`（`order/model/order_spent_model.go`）
与计入消费的状态名单 `paidStatuses`（`order/model/order_model.go` 声明一次）。
**新聚合不得复制这两个口径的第二份文本。**

### 4.2 analytics（够用，无需新增）

`Summary` 已提供：`Total` / `Visitors` / `Daily`（按天 PV·UV）/ `Paths`（按路径聚合，带游标）/
`Referrers` / `UAClasses` / `Langs`。

已知缺口（本方案接受，不在第一轮补）：「按天 × 路径」的交叉排行——悬浮显示「那天哪些页面」需要新查询，
第一轮退化为「窗口内页面前十」。

### 4.3 page

| 接口 | 用途 | 现状 |
|---|---|---|
| path → kind 映射（按工程） | 把 analytics 的路径排行切成「页面 / 文章」两类 | 无；`pages` 表有 `kind`（home / archive / search / notFound / page / article / tag） |

### 4.4 user（客户域）

| 接口 | 用途 | 现状 |
|---|---|---|
| 客户增长（新客 / 复购 / 回头客） | 客户概览面板 | 无 |
| RFM 分段与分群 | RFM 分析页 + 客户列表筛选 | 无 |
| Cohort 留存矩阵 | Cohort 分析页 | 无 |

口径取自 Laravel CRM（`/home/sky/project/php/laravel/crm/example-app/app/Services/Woocommerce/Reports/`），
**只搬口径不搬实现**：

- 新客：按**首次下单**所属区间归属（不看注册时间；注册但从未下单不计入）。
- 复购：区间内订单数 ≥ 2；复购率 =（新客复购数 + 老客下单数）/ 区间下单客户数。
  CRM 按邮箱判人，go_wp 一律按 `user_id`。
- RFM：三段各五分位；**金额阈值必须按本项目客单价重定**（CRM 的 ≥300 / 180-299 / … 是欧元尺度，
  go_wp 金额单位是分），R 天数与 F 次数的分档口径可原样沿用。
- Cohort：按首单所在月分群 + 留存矩阵。
- 生命周期等级（Starter / Silver / Gold）：CRM 按首月龄分层，**与现有 membership 会员等级冲突**，
  必须映射到现有等级或舍弃，不允许两套等级并存。

## 5. 分批计划

每批独立可验收。「闸门」= 能变红的检查，不接受「看起来对了」。

### P0 · 常驻层：AI 读的站点规则
- 交付：一份给 AI 的规则文档（口径、红线、术语），明确复用 `AGENTS.md` 的判据而非另写一套。
- 闸门：该文档进入提示词**稳定前缀**，同一会话两次请求的前缀逐字节一致（`docs/16` §3 的静态断言扩展）。

### P1 · 按需层：模块能力手册
- 交付：每个模块一篇（有哪些表、什么口径、有哪些工具、注意事项）+ 一份目录摘要；素材来自
  `13-module-inventory.md` 与各模块 `CLAUDE.md`。
- 闸门：AI 在不知道任何 schema 的情况下，能把「本店这周卖得最好的是什么」定位到正确模块与工具。

### P2 · 数据接口：order 聚合
- 交付：§4.1 的四个接口（model 层聚合 + service 只读方法 + 模块内单测）。
- 闸门：`go test ./internal/module/order/...` 通过；口径断言测试证明净额与 `orderNetTotalSQLExpr` 同源
  （改一处必须让两处同时红）。

### P3 · 能力层：工具注册表 + agent loop
- 交付：
  · 各模块 `inbound/mcp` 下声明工具（权限点 + 参数 schema + handler），装配期汇总成注册表；
  · ai 模块补 **tools 往返**：`ai_protocol_chat.go` 与 `ai_protocol_responses.go` 两条协议各自的请求构造与响应解析；
  · agent loop（多轮工具调用，带轮次上限与每轮事件落库）。
- 已知必须同批修的既有假设：两条协议的解析函数目前把「正文为空」判成 `ErrInternal`
  （`parseChatCompletionsReply` 取 `choices[0].message.content`），而模型要调工具时正文**本来就是空的** ——
  不同批改掉，第一次工具调用就会报错。
- 闸门：模型连续调用 ≥2 个工具后给出正确结论；工具调用与结果在事件日志中**成对**（`docs/16` §2.3）。

### P4 · 治理层：审批 + 审计 + 工具结果剪枝
- 交付：
  · 写工具一律二次确认（复用 `ui/confirm.js`），高风险动作要求显式参数确认；
  · 工具调用落审计（谁 / 何时 / 哪个工具 / 参数摘要 / 结果 / 耗时 / 来源）；
  · 工具结果剪枝（`docs/16` §2 第 1 条「工具结果截断」，先剪枝后摘要），参数参考
    Anthropic context management 的 `clear_tool_uses`（按 token 阈值清理旧结果、保留最近 N 次）。
- 闸门：一次写操作能追到人、参数、结果、时间；大结果查询后上下文占用不越界（压缩开销占比 ≤2%）。

### P5 · 表现层：spec 渲染器
- 交付：spec 类型与校验器（white-list，Go 侧）+ Jet 片段渲染器 + `WBUI.scan` 挂载；
  首批组件：`stat` / `table` / `list` / `accordion`。
- 闸门：未知组件类型与未知字段被拒绝且降级为纯文本回答（不允许白屏）；渲染出的表格与手写页面视觉一致。

### P6 · 消费端：概览页重构
- 交付：时间筛选条（今日 / 昨日 / 本周 / 本月 / 本年 / 自定义）+ KPI（订单卡两格 / 页面浏览总量 /
  商品销售总量 / 新客户）+ 图表两个 Tab（销售额与订单、浏览量）+ 排行榜两个 Tab
  （热销商品前十、页面前十）。
- 依赖：P2（order 聚合）、P5（如果 KPI 卡要支持 AI 生成的可切换形态）。
- 闸门：KPI 可点击跳到对应筛选的订单页；空库时全部显示 0 而不是报错。

### P7 · 消费端：客户目录
- 交付：新建一级目录「客户」（客户概览 / 客户列表 / RFM 分析 / Cohort 分析），原「交易」更名「订单」；
  客户列表加筛选：新老客、复购次数、RFM 分段、会员等级、注册时间。
- 依赖：§4.4 的客户域接口。
- 闸门：客户概览的三个数字与客户列表按同条件筛选出的条数一致（对账测试）。

### P8 · 对外：MCP 端点 + PAT
- 交付：官方 go-sdk 暴露 `/mcp`（streamable HTTP）；PAT 令牌表与生成 / 吊销页面；令牌解析中间件
  （解析成 admin 身份后走现有 Casbin）；`/mcp` **默认关闭**，显式开启才生效；按 token scope 裁剪 `tools/list`。
- 闸门：无令牌调用一律拒绝；越权工具调用返回 403 且落审计；令牌吊销后立即失效。

## 6. 风险与待定

| 项 | 说明 | 处置 |
|---|---|---|
| 本机库基本是空的 | `pages` / `contents` 查不到数据，概览页所有数字会全是 0 | 动工前定造数方式（种子或连真库），否则 P6 无法验收 |
| 工具集与前缀缓存的取舍 | 按角色裁剪工具清单会让每个角色一套前缀 | 已定 D4：内部统一、外部按 scope |
| AI 认错页面或维度 | 误判比不给更糟 | 回答里明说自己的理解，模糊时先问一句；动作一律先给按钮不自动执行 |
| 跨模块组装点 | 概览页要同时用 order / analytics / page / project 的数据 | 组装点定在 workbench 的 Dashboard（现职），跨模块只走 contract；若契约面变重再评估独立装配层 |
| spec 校验失败 | 模型输出不稳定 | 降级为纯文本回答，并落一条诊断事件（不静默丢） |
| 「一级菜单点击进概览」 | 现有侧栏支持两种一级形态，但现有目录都带子菜单 | 采用「二级第一项 = XX 概览」，不改造一级项交互 |

## 7. 与既有约定的核对

- 不变量 1（控制面/访问面分离）：AI 助手与概览页全在控制面，访问面仍是只读静态直出，不受影响。
- 不变量 4（Binding 不是 Query DSL）：spec 与工具参数都是白名单受限形态，不接受任意过滤表达式或 SQL。
- 表隔离：工具与聚合一律由拥有该表的模块提供，概览侧只组合 contract 返回值。
- 事务与回滚：本方案新接口**全部只读**；写操作只出现在工具层，逐个按 `AGENTS.md` §写操作执行。
- i18n：新增页面与 AI 输出文案走 `sys_i18n`，不写死中文。
- 多端：悬浮球与概览页按 1440 / 768 / 375 三视口 × 鼠标 / 触屏 / 键盘验收（`docs/rules/frontend.md`）。

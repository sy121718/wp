## 0 判据与分类口径

### 0.1 降级链（判据的物理基础）

`pkg/i18n/translate.go:27-40` 是取词的唯一实现，链序：

1. 命中当前语言 → 返回译文；
2. 未命中当前语言 → 回退默认语言（`i18n.GetDefaultLang()`，默认 zh-CN）；
3. 仍未命中（key 不存在 / 未初始化 / key 为空）→ 返回调用方写的中文 `fallback`；
4. `fallback` 也为空 → 返回 key 本身。

判定式是 `if text := GetText(key, lang); text != "" && text != key { return text }`。
**推论一**：`fallback` 是中文时，「key 查不到」的可见后果是**中文照旧显示**，不是裸 key —— 这类缺口不会自我暴露。
**推论二**：译文值为空串（`''`）与「没有这一行」在运行时等价，二者都走 fallback —— 缺译文要按「缺行 **或** 空串」两类一起算。

库内实测（`SELECT count(*) FROM sys_i18n WHERE item_key ~ '[一-鿿]'`）：**中文 item_key = 0 条**。
所以「拿中文当 key」必然查不到 —— 这是分类②的物理依据。

### 2.1 `admin.inventory.moves.heading` 是否存在

**结论：这个 key 不存在 —— 模板没引用、库里没有，且这个名字本身疑似上游笔误。**

- 模板全目录（111 个 `.html`）检索：`admin.inventory.moves.heading` **0 命中**。
- 库内 `LIKE 'admin.inventory.moves%'` 实测 **17 个 key × 2 语言 = 34 行**，全部中英成对：`.title` / `.titleLead` / `.titleTail` / `.hint` / `.empty` / `.emptyHeading` / `.emptyLead` / `.emptyPurchaseLink` / `.emptyTail` / `.col.{time,warehouse,direction,delta,qtyChange,reason,sourceRef,operator}`。
- 模板真正引用的是 `admin.inventory.moves.title`（`internal/templates/admin/inventory/inventory.html:68`）与 `.emptyHeading`（同文件 `:213`），二者库里都有。
- 「heading」这个词来自**迁移 442 的文件名**（`442_i18n_inventory_moves_heading.sql`，内容就是 `admin.inventory.moves.title`），不是 key 名 —— 上游很可能把文件名后缀当成了 key。
- 上游提到的「迁移 445 的名字是 inventory reason bulk」**核实成立**：`public/migrations/445_i18n_inventory_reason_bulk.sql`，与 moves heading 无关。

### 2.2 `scripts/check-no-internal-error-leak.sh` 的判据，以及 workbench 38 处为何没被抓

**判据（读脚本头部注释与实现得到，非照抄）：候选集 = 各模块 `inbound/http` 下所有含字面量 `.Error()` 的行；每条候选再判是否命中三种「送进响应」形态之一。**

- 候选获取：`grep -rn --include='*.go' -F '.Error()'` 于 `find internal/module -type d -path '*/inbound/http'`，剔除 `_test.go` 与整行注释。
- 形态 ①：`RESPONSE_CALL_RE='([A-Za-z_][A-Za-z0-9_]*\.(ErrorWithMessage|ParamError)|c\.String)\('`
- 形态 ②：`SHAPE2_RE='(\?err=|QueryEscape\(|Redirect\(|RedirectWith)'`
- 形态 ③：`SHAPE3_RE='(Errors|Errors:)'`
- 三种都不命中 → `continue`，**不报**。

**workbench 的固定中文 `c.String` 为什么没被抓**：那些行的实参是**中文字符串字面量**，整行里**没有 `.Error()`** —— 因此**根本不进候选集**，连形态判定都不会发生。门禁的定位是「禁止直出内部错误（防泄漏表名 / SQL / 路径）」，不是「禁止未 key 化的中文」，两类判据不同。

实测数量（2026-09-26）：workbench 后台 handler 下 `c.String(http.StatusXxx, "中文…")` 共 **41 处** —— `workbench_handle.go` **30** / `workbench_preview_handle.go` **8** / `workbench_instance.go` **3**（上游给的 30 + 8 = 38 **正确**，另加 `workbench_instance.go` 的 3 处；上游漏计这 3 处）。另有 5 处 `c.String` 走非字面量（`workbench_err.go:239,246,251`、`inspector_handle.go:159,166`），其中 `inspector_handle.go` 走 `shell.PageInternalText(c)` 属正确形态。

实跑结果：`✓ 未发现直出内部错误的调用点（已扫描 24 个 inbound/http 目录）`，退出码 0 —— **门禁绿，但与 i18n 覆盖度无关**。

### 2.3 `cmd/i18n-orphan` 是做什么的，与本次审计的关系

`cmd/i18n-orphan/main.go` 是**内容译文（CMS 内容实例的译文行）的孤儿清理运维命令**（审计 I18N-024），与后台 UI 词条**不是同一套数据**：

- 它的作用域是「某个工程（`-project` 必填）+ 语言」下的**内容译文行**，判据由 `pkg/i18n/content_orphan.go` 定义（hash 自洽破损；提供 `-keep-file` 时再加「源引用消失」判据）；默认 dry run，只有 `-apply` 才删。
- **它既不检测「模板引用了但库里没有的 key」，也不检测「库里没人引用的孤儿 UI 词条」** —— 它的输入是「内容 hash + context」，不是 UI 词条表 `sys_i18n` 的 `item_key`。
- 与本次审计的关系：**无关**（同属 i18n 域，但一个是内容层译文清理，一个是后台 UI 词条覆盖度）。本次审计缺的那条检测——「模板 / Go 侧引用了但 `sys_i18n` 里没有的 key」——**仓库里目前没有专门门禁**（见 §4）。

## 4 门禁与制度的盲区

### 4.1 模板门禁只覆盖 `internal/templates/admin/**/*.html`，Go 侧完全不在扫描范围

实跑（2026-09-26）：

```

✓ 与基线一致（0）
```

基线文件 `scripts/i18n-coverage-baseline.txt` 内容为 `0`。**盲区三条**：

1. 范围为 `admin/` 一个目录 —— `internal/templates/fragments/`（7 个片段，6 个零 `t()`）与 `internal/templates/workbench/layout.html`（零 `t()`）**都不在扫描面内**；

3. 它只数「未 key 化的中文行」，**不检查引用的 key 在库里有没有词条** —— 把中文改成 `t("一个库里不存在的 key", "中文")` 会让这个门禁**变绿**，而英文界面照旧是中文。

### 4.2 430 的对账只扫 enums 包（且只认点分 + 只覆盖 5 个模块）

`public/migrations/430_i18n_enums_missing_keys.sql` 头部自述其口径：用 `go/parser` 扫 `internal/module/*/enums/*.go` 的 728 个常量，按**值形态**筛出 key 再对账。

现行常态化的那条对账是 `public/test/enums/unit/enums_key_seed_test.go`，判据更窄：

- 模块清单**只有 5 个**：`cart` / `order` / `user` / `mail` / `workbench`（`enumsFiles` 变量）—— admin / page / block / navigation / product / inventory / project / content 等模块**不在清单**；
- 文件范围只有 `enums/*.go` —— **handler 层的常量不在扫描面**；
- key 正则 `^\s*(?:const\s+)?\w+\s*=\s*"([a-z][a-z0-9]*\.(?:msg|err|test)\.[A-Za-z0-9_.]+)"` 只认**点分且首段小写、第二段是 msg|err|test** 的形态 —— **裸名 key（如 `MsgInternalError`、`ErrInvalidParam`）一律不匹配**。

这正是 §8.1 第 3 条 那 13 条只有 zh-CN 的 `Msg*` 逃过对账的原因：它们**定义在 `internal/module/*/inbound/http/` 的 handler 层**（`admin_pages_handle.go:39-45`、`block_page_handle.go:29`、`navigation_page_handle.go:33`、`theme_admin_pages.go:33`、`theme_settings_admin_pages.go:32`、`site_settings_admin_pages.go:36`），既不在 5 模块清单、也不在 enums 目录、值还是裸名形状。

### 4.3 没有「词条中英成对」的校验

全库实测：`SELECT count(*) FROM (SELECT item_key FROM sys_i18n WHERE lang='zh-CN' AND item_key NOT IN (SELECT item_key FROM sys_i18n WHERE lang='en-US'))` = **13**。

这 13 条正是 §8.1 第 3 条 的 `Msg*` 家族，而它们能长期存在，是因为**没有任何门禁检查「一个 key 是否中英都有行」**：模板门禁不查库、enums 对账只查 5 模块的点分 key、`cmd/i18n-orphan` 管的是内容译文。空串同理（全库 1 条：`admin.product_categories.children.pageSuffix` 的 en-US = `''`）。

## 5 正确形态的既有先例

### 5.1 `runtimefragment` 的 key + fallback + 请求取词

`internal/module/runtimefragment/fragment_i18n_orders.go:115-124`：

```go
func orderStatusLabelOf(r *Request, status string) string {
	if r == nil { return orderStatusFallback(status) }
	key := "site.fragment.order.status." + status
	fallback := orderStatusFallback(status)

```

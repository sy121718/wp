# i18n 细则 —— 词条、占位符与回执通道

`AGENTS.md` 里与 i18n 相关的判据只有几句（错误文案三件套、`sys_i18n` 主键 `(item_key, lang)`、
`enums` 不硬编码响应文案）。这份文档记的是**为什么这么定**、以及**哪些做法看着能用其实会坏**。

## 一、词条形态的两条硬约定

### 1. 参数占位符用 `{name}`，不要用 `%s` + `fmt.Sprintf`

两条静默故障，都是实测：

- **词条会被运营改**。后台词条管理页改出裸 `%`（如「折扣 50%」）时，`Sprintf` 会把它当格式化动词
  → 页面输出 `%!s(MISSING)` 一类乱码。库中现存**含裸 `%` 的词条**，这不是假想。
- **中英占位符数量/顺序不一致时静默错配**：位置参数没有防护，译者调整词序（zh `{a}…{b}` vs
  en `{b}…{a}`）就把 A 的值填进 B 的位置，页面显示错误的数字或节点名。

命名占位符把这两条都变成**可判定**的：填完还剩 `{xxx}` 就是没填干净，调用方丢弃该条、落兜底文案。
公共实现在 `pkg/i18n/placeholder.go`：`FillNamedPlaceholders` / `FillTranslate`（后者在词条被改坏时
自动回落代码里的中文兜底）/ `HasNamedPlaceholders`。

**存量 `%s` 词条与它们的消费代码按批次迁移，不要在一次改动里全量替换。**

### 2. SQL 里写换行用 `E'...\n'`，不要用 `'...\n'`

PostgreSQL 的**普通字符串不解释转义**：`'a\nb'` 的值是 `a` + 反斜杠 + `n` + `b`（四个字符里的两个），
只有 `E'a\nb'` 才是真的换行。项目里已有先例（`244` / `262` 的 `string_agg(..., E'\n')`）。

实测踩过：同一个 key 的 zh-CN 写成 `'…。\n'`、en-US 写成真换行（字符串跨行），两边在 SQL 文件里
**都看着正常**，但值不同形 —— 词条未 seed 时走 Go 兜底（真换行）、已 seed 时走库值（字面 `\n`），
同一句文案随「词条是否已入库」变样。

判据：不要读 SQL 文件判断，查真实字节 —— `encode(convert_to(item_value,'UTF8'),'escape')`。

## 二、空串在降级链里等同缺失

取值链的命中判据是 `text != "" && text != key`（`pkg/i18n/translate.go`）。于是**某语言把词条留空，
取值会静默回落到默认语言**。

实测：英文习惯是 `Page 3`、不需要后缀，于是把分页后缀的 en-US 留空 → 英文界面渲染成 `Page 3 页`。
不报错、不 500、日志干净，只是混进一句中文。

要表达「这段在本语言为空」不能用空串，得换形态：把整句收成一个带 `{name}` 的词条
（`第 {page} 页` / `Page {page}`），或按语言分支。

**检查多语言词条时把「值非空」当硬条件** —— 空串与缺行是同一个故障。判据：

```sql
-- 期望 0
SELECT count(*) FROM (
  SELECT item_key FROM sys_i18n WHERE lang='zh-CN'
  EXCEPT
  SELECT item_key FROM sys_i18n WHERE lang='en-US' AND item_value IS NOT NULL AND item_value <> ''
) t;
```

## 三、seed 迁移的门槛判据

词条用迁移 seed，`ConditionSQL` 的门槛**必须枚举本批自己的 `item_key`**（上界封闭）。见
`AGENTS.md` §数据库·迁移 的两条判据，两个方向的真实故障分别记在 `database.md`。

本目录相关的补充：**增删词条时门槛的计数要同批改**。452 交付时改过一次 —— 词条从 144 涨到 151
（补了 `workbench.ui.inspector.*` 的 7 处裸中文），门槛从 `= 288` 跟着改成 `= 302`；两处不同步的
表现是「每次启动都重跑」（计数永远追不平），而不是报错。

**验收手法（执行完 seed 后固定做一遍）**：把注册文件里拼接后的**真实 `ConditionSQL`** 抽出来
交给数据库执行，**期望返回 1**：

```python
src  = open('public/migrations/register_xxx_i18n.go', encoding='utf-8').read()
expr = re.search(r'ConditionSQL:\s*(.*?),\n\t\tSQL:', src, re.S).group(1)
expr = "\n".join(l for l in expr.splitlines() if not l.strip().startswith('//'))  # 去 Go 注释
cond = "".join(re.findall(r'"((?:[^"\\]|\\.)*)"', expr))                          # 拼接字符串字面量
# 执行 cond，取「数据行」而不是末尾的 (N rows, Xms)，期望 [[1]]
```

返回 **0** 就意味着每次启动都会重跑这条 seed。这条判据比人眼看「248 / 284」可靠 ——
449 与 452 两次故障都是「门槛数字与内容不同步」，**两次都是靠人眼发现的**，而它本可以机器判定。

**另一个坑：门槛的 `IN` 列表本身也会漏**。449 的实际故障是双重的 —— 数字停在 248（改 284 后）、
而 `IN` 列表里只有 124 个 key 而 SQL 有 142 个（差的那 18 个 `admin.product_translations.*`
在补进 SQL 时忘了同步注册文件）。所以上面那条执行判据是必须的：**只看数字对不对不够，
要让数据库按真实 SQL 算出计数**。

## 四、URL 回执通道：两套机制并存，以及一个**已知限制**

列表页的写动作会把结果回带到下一页，走 `?err=` / `?ok=` / `?done=`。这里有**两套机制**：

| 机制 | 形状 | 用法 |
|---|---|---|
| `shell.FacingQueryText` / `FacingNotice` | 写侧拼**成品句子**（按当前语言取词），读侧按**整句候选比对**（数字归一） | 存量，13 处调用 |
| `shell.SetFacingNoticeQuery` + `FacingNoticeText`（`internal/web/shell/notice_param.go`） | 写侧只传 **key + 整数计数**，读侧按当前语言取词并填 `{n}` 占位符 | **新回执用这套** |

第二套还顺带堵住了「手拼 URL 伪造系统提示」——第一套靠枚举候选整句来防，第二套靠 key 白名单 +
计数范围（`Param.Max`）+ 输出前残留判据。

### 已知限制：存量回执在跨语言场景会丢

存量回执由**写侧按当前语言拼句**，读侧再用**同语言**的候选表比对。于是：

> 在中文界面提交 → 302 回列表页的 URL 里是中文字句子 → 用户先切到英文、再打开那个 URL
> → 读侧用英文候选比对中文句子 → 不命中 → **回执落空**（页面不显示「刚才是 3 个没做成」）。

**同语言下完全正常**，这只是一个窄场景的缺陷。

### 为什么不把存量回执全量迁移

评估过（2026-09），结论是**成本高于收益**：

1. `notice_param.go` 的形状是「**一个固定句子 + 至多 4 个整数参数**」(`noticeMaxParams = 4`)，
   而存量回执大多是**条件拼段**的动态句子 —— 例如客户批量动作是「前缀 + 分段 + 句号」，分段数
   随计数变化（仅成功 / 仅跳过 / 两者都有），解锁动作 3 个计数 → 7 种组合。spec 只能靠**选哪个
   key** 表达「哪些段出现」（`Keys` 是 map，天然支持），代价是**每个组合一个 key**：customer 一个
   页面就要 10 个 key（3 + 7）。
2. 调用点 13 处，每处背后还有各自的**模板候选表**（如 `mailFormNoticeTemplates` /
   `mailCountedNoticeTemplates`），都要重写。
3. 收益只覆盖上面那个窄场景。

**因此的约定**：**新回执一律用三件套**（`SetFacingNoticeQuery` + `FacingNoticeText` + 包级
`FacingNoticeSpec`），存量保持现状。上面那条限制如实记在这里，不要据它推断「回执机制不可靠」。

### 相关的门禁

`internal/module/admin/inbound/http/admin_err_texts_test.go` 用正则守着 URL 通道的写法形态
（只认 `"?err=" + url.QueryEscape(EXPR…)` 与 `adminI18nBackURL(c, "err"|"errored", …)` 两种）。
**改 URL 通道的写法必须同批改它**，否则门禁红。

## 五、Go 侧取词的形态清单（扫漏一种就是漏一半）

统计「某个模块还有多少内联 key」时，只认一种调用形式会得到**假归零**。实测清单（2026-09）：

```go
tr("admin.x.y", "中文兜底")                            // ① 直调
i18n.Translate("admin.x.y", "中文兜底", lang)           // ② 带语言的直查
i18n.FillTranslate(tr, "admin.x.y", "中文兜底", params) // ③ 命名占位符填充
shell.FacingQueryText / FacingNotice(…)                // ④ URL 回执通道（形态不同，另行收敛）
response.SuccessWithMessage(c, "admin.x.y")            // ⑤ 归口 key（response 层取词）
response.ErrorWithMessage(c, code, "admin.x.y")
```

**踩过的地方**：第一版扫描只写 `tr\("…"`，block 模块扫出 4 处并对它们做了替换，复查时才发现
`block_err.go` 还有一处走 `i18n.FillTranslate(tr, "admin.blocks.usage.more", …)` —— 形态 ③ 完全不在
判据里，于是「残留已归零」是假的。

**正则两个方向都会错**：

- **写窄**（漏）：`FillTranslate\([^,]+, *"…` 匹配不了实参里含逗号的调用（`FillTranslate(shell.TranslateFor(c), "…")`）；
  多行实参更是任何单行正则都盖不住。
- **写松**（误报）：`tr\("[a-z]` 会把 **`strPtr("smtp")`** 匹配进来（`tr` 是 `strPtr` 的子串）——
  实测被它误导过一次：扫描报 mail 模块「7 处残留」，逐条看全是 `strPtr("smtp")` / `strPtr("manual")`，
  实际是 0；另有几处命中其实是**注释里的示例**（`// 调用点原先直接写 key 字面量（tr("…", "…")）`）。

所以取词扫描要用**词边界**并**排除注释行**：

```bash
rg -n --type go '\btr\("[a-z]|i18n\.Translate\("[a-z]|i18n\.FillTranslate\([^)]*"[a-z]' <模块>/ -g '!**/*_test.go' \
  | grep -vE ':[0-9]+:\s*(//|\*)'
```

**扫完必须人眼复核一遍**「该目录下所有含点分 key 字面量的行」，别把扫描结果当结论
（同 `AGENTS.md` 铁律 7／14：读数异常先怀疑判据 —— 无论是「数目异常大」还是「异常为 0」）。

**归零的验收口径**：`rg -c --type go 'tr\("[a-z]|i18n\.Translate\("[a-z]|FillTranslate\([^)]*"[a-z]' <模块>/ -g '!**/*_test.go'`
要真的为 0，且**同时**确认 `go build ./...` 与 `go test <模块> -count=1 -p 2` 是绿的 —— 替换常量时写错值
（常量值 ≠ 原字面量）不会编译报错，只会让词条取不到、页面回落中文。
